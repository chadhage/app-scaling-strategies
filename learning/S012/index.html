S012 — CPU/memory-driven scale-out

A-S012 · D-S012 · SC-S012 · one frozen satisfier (S), kanoUnit A-S012

Objective: scale before resource saturation causes queuing or latency-budget violations. A rule trigger and a requested instance are not evidence of effective capacity or successful users.

Declared synthetic fixture

  • Start: two ready instances. Each represents 100 CPU units, 100 memory units, and 100 requests/second.
  • Rule: CPU ≥ 70% OR memory ≥ 75% for two consecutive 10-second windows; add one instance. Warm-up takes two more windows. Maximum: four instances. No automatic scale-in.
  • Percent = aggregate resource units ÷ ready instances, capped at 100% in the metric display. Raw demand above 100% and saturation are retained separately.
  • Each Observe ten journeys samples ten fixed synthetic clients independently of metric windows. A correct journey completes, preserves session/cart state, produces one effect, and meets its latency budget.
  • Latency model: 80 ms + ceil(queued requests/second ÷ service requests/second × 1000). Saturation adds 300 ms + ceil(raw resource percent − 100). These are teaching constants, not Azure thresholds or performance predictions.
  • Missing data is UNKNOWN; unsupported profiles do not run. HTTP automatic scaling is not this CPU/memory rule. Actual metric, SKU, plan and slot eligibility require separate native qualification.

Preconditions and limits: a modern browser with JavaScript; no server or cloud access. No real CPU load, memory allocation, telemetry, autoscale profile, subscription, slots, identity, deployment, or spend. Node.js 22 is test tooling only; production Node.js 24 and native B-S012/D-S012 acceptance are unvalidated.

Conduct the preemptive transition

  1. Keep the defaults; observe ten baseline journeys.
  2. Advance two metric windows. CPU triggers a request: requested 3, effective ready 2.
  3. Observe ten journeys during warm-up; advance two more windows. Effective ready becomes 3 and CPU falls to 46.67%.
  4. Observe ten post-scale journeys. Inspect added-instance use, all 30 outcomes, and the exercise verifier.
  5. Reset, then try CPU 40 / memory 150 to trigger on memory alone. Or CPU 260 / offered load 260 to measure saturation, queuing, and interruptions before recovery.

Every action is explicit; nothing advances on a wall clock. Changing controls does not rewrite a recorded trace. Apply changes before stepping. Apply restarts the breach streak but does not cancel an in-progress request.
