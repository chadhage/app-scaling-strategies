S019: Cell-based expansion

Objective: Add an isolated application cell and migrate a selected tenant through controlled state and routing handoff. Distinguish added capacity, a copied snapshot, exclusive write ownership, and a route.

Preconditions and limits: Cell A owns alpha (writes 1, 2) and beta (write 1) at epoch 1. Its two ready synthetic workers provide 100 requests/second. Creating B adds two distinct workers and an isolated empty store: another 100 synthetic requests/second, not a deployment slot. Two tenants, two cells, 48 actions, 8 two-tenant journey batches, 14 acknowledged writes per tenant, and four archived runs in page memory only. Reload clears everything.

Conduct the handoff

  1. Choose a tenant before the first action. Try routing early: the guard preserves source service.
  2. Create B and synchronize the selected tenant. Commit a source write to make that snapshot stale; attempt ownership transfer and see it blocked. Synchronize again.
  3. Transfer exclusive ownership (A epoch 1 is fenced; B gets epoch 2), then route the selected tenant. These are separate controls: a journey in the gap fails visibly with HTTP 409.
  4. Exercise the old writer and run both tenant journeys. Inspect ordered writes and the unaffected tenant remaining in A.
  5. After routing, select an unready, wrong-state, or unknown B observation and run journeys again. HTTP 200 with wrong business state is a failure, not success. Restore healthy observations: earlier failures and unknowns remain cumulative.
  6. Archive and reset to compare a clean run. Each synthetic success requires both tenant journeys and an actual old-writer rejection.
