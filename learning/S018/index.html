Independent tier scaling

Scale the constrained tier while preserving contracts and capacity limits in remaining tiers.

The declared synthetic fixture

Ten journeys cross frontend → API → worker per window. Every server instance is assumed ready immediately. The selected bottleneck handles 6 journeys/instance/window; the other tiers each handle 12. This is a fixed educational model, not measured Azure behavior.

  • The frontend server has no database pool. Each API and worker instance fills 4 database connections in the observation window.
  • The unchanged database limit is 12 occupied connections. Each excess connection causes one admitted journey to fail acquisition at 200 ms, bounded by the admitted count.
  • A healthy journey takes 100 ms; the original journey budget is 150 ms. Journeys beyond tier capacity miss that deadline at 175 ms, 200 ms, and so on.
  • A broken tier contract fails every admitted journey, even at 100 ms. Missing downstream completion evidence leaves admitted compatible journeys UNKNOWN, not successful.

Preconditions: one instance per tier, compatible v1 contracts, no real users or resources. No provisioning, warm-up, routing, native database connections or production runtime is exercised.

  1. Choose a bottleneck before the first command. Change only that tier to 2, then observe: ten successful journeys should fit all budgets.
  2. Archive/reset. Try a wrong tier, or compare scaling every tier to 2: extra backend pools can transfer pressure to the database.
  3. Try incompatible contracts or missing evidence. Correct the condition and observe again: recovery cannot erase earlier FAIL or UNKNOWN.
