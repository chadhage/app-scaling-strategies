Shadow getProfile: compare responses, contain effects

Production answers the caller. A separate candidate sees a synthetic copy. Does a matching response mean replay was safe?

Objective and preconditions

Keep caller responses on the intended production version, compare status and business fields with the other version, and check effects independently of response equality.

Both versions already exist as local fixtures. There is no deployment or routing change. Two fictional profiles are available; arbitrary profiles, endpoints and real traffic are not supported.

A read-looking operation can still have effects. In this fixture, each production getProfile records one profile-view write and one notification. The candidate attempts the same actions through a separate shadow sink. A safe sink suppresses both; the explicitly unsafe fixture records duplicates only in local counters.

Try: replay safe shadow, then discrepant response, then unsafe duplicate effects. Notice that unsafe responses still match. Replay safely again: the earlier duplicate counters must remain. Try unknown and invalid input, then Reset. Repeat with production v2.

Limits and native follow-up

  • Every profile, response, request and effect is a deterministic synthetic fixture. No HTTP request or real replay is made.
  • UNKNOWN deliberately withholds a response after the candidate's suppressed effect attempt. It cannot establish response correctness; known synthetic sink counts do not prove a real candidate is safe.
  • This finite exercise does not prove live platform routing, authorization, load behavior, data compatibility, notification isolation or production readiness.
  • Real shadow designs need an approved isolated environment, data handling, effect suppression and measured evidence. This lesson grants no permission to replay into production or cloud.
  • No native B-S009 result or completed D-S009 parent is claimed. Node tests are not browser proof; actual browser observations are recorded separately in evidence.json.
