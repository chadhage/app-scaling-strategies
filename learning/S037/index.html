S037 — Session serialization change

Read existing sessions while old and new code coexist. A new reader alone is insufficient: old code must still read candidate writes for coexistence and rollback.

Preconditions: one synthetic cart in an assumed shared in-memory fixture; v1 reads schema 1 only. No account, server or credentials are needed.

  1. Keep the compatible defaults; check and attempt transition, then roll back.
  2. Try a schema-2-only reader, schema 2 writes, or the faulty silent-reset reader.
  3. Compare preserved, failed and unknown read probes. Reset starts an untested run, not a repair.

    What this rehearsal does not prove
    
      
    This deterministic, read-only fixture illustrates schema compatibility, silent data loss and a
        pre-exposure gate. It does not implement a session store, serializer library migration,
        authentication, routing, concurrent writers, real rollback, Azure, durability or a reliability SLA.
        No identities, tokens, keys, management APIs or storage are used.
    
      
    A failed or unknown probe blocks the synthetic transition. Detecting a fault is not an uninterrupted
        migration; no real user transition was measured. B-S037 native proof and whole D-S037 acceptance remain separate.
