Can the next canary cohort advance?

Objective: advance a staged canary only after complete, fresh journey evidence. Try a healthy stage, then see a regression stop the next increment.

Preconditions and operating envelope

These are assumptions, not measured readiness: invented v1 and v2 are warm, compatible, have overlap capacity, and preserve authentication and state. v1 remains available for recovery. No application framework or hosting target is selected.

  • 20 invented users u01–u20 start on v1. Stable cohorts always expand in ID order.
  • Every complete journey must preserve login/session and state, create exactly one effect, return HTTP 2xx, and finish within 1000 ms. HTTP 200 alone is insufficient.
  • Observe all 20 users for the configured simulated window. Evidence expires after 60 seconds and belongs to one stage epoch only.

1. Configure the local rehearsal

A 5% rehearsal is already started. Starting again or clearing explicitly discards this local history. Normal promotion and rollback never erase it.

2. Observe, decide, inspect

Worked path: record Safe complete journeys, promote from 5% to 25%, then record Regressed journey and try another promotion. Expect a blocked 50% increment, with the interruption retained. No real time elapses.

Blocked attempts are deliberately clickable so you can test the guard. They record a refusal, not an increment. A failed or unknown attempted transition cannot be repaired retroactively by a later passing probe; start a separate rehearsal to try a new transition.

      Scope, limits and reproducibility

      • SOURCE-only learning exercise. IaC: N/A — no Azure resource is needed. C001 runtime/authentication/hosting approval and separate scaffold/deploy approval are absent.
      • No credentials, cookies, browser storage, package dependencies, service workers, management calls or network requests. State is local, ephemeral and not shared with other lessons.
      • Deterministic fixtures, 20 invented users and a simulated clock do not establish native routing, authorization, production capacity, recovery, drain completion or old-destination retirement.
      • A negative educational verification can pass while a user is interrupted. Neither B-S003 native proof nor full D-S003/source acceptance is delivered. The sample proves no 99.999% reliability or uninterrupted live migration.
