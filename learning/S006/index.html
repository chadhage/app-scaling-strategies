Who may enter the preview?

An obscure address is a location, not authorization. Keep GA users on v1 while checking approval at every candidate entry.

Objective & preconditions

Compare an approved identity, a non-approved visitor, and unknown identity evidence across ordinary navigation and direct/indirect preview paths. Inspect the trace and check the independent oracle, not just a success label.

  • Two independent synthetic client sessions: GA ga-session-001 and probe preview-session-001. The companion GA client keeps its subject, attribution, and v1 route.
  • Approval and callback binding are predefined teaching fixtures, not real authentication. Status codes are model outputs, not HTTP responses.
  • All route strings are inert. No real redirects, requests, auth APIs, cookies, tokens, credentials, or management calls occur. Automatic candidate routing is fixed at 0% in both policies.
  • Ordinary v1 navigation represents routing only; it does not bypass or replace production login or reveal personal data.

Worked exercise: prove the boundary, then break it

  1. Run the default approved identity with Join authorized preview. Expect v2, synthetic 200, and login → bound callback → per-request approval. GA attribution must not change.
  2. Select the non-approved visitor and Direct candidate API. Expect forbidden / 403, even if the visitor knows /candidate-7f3b/api/getProfile. Try an indirect route too.
  3. Try missing identity evidence. Expect unknown / 401 and no candidate service. Compare all routes retains these outcomes beside approved and denied probes.
  4. Select the deliberately broken obscure-URL-only policy. The same visitor reaches v2: the verifier must FAIL and user impact must show unauthorized exposure, despite 0% automatic routing.
  5. Return to the enforced policy; use an approved identity with a mismatched callback. Expect callback rejection, not a successful preview visit. Reset explicitly when finished.

    Limits & next real gates
    
      
      
        
    • This is a browser-editable instructional model, not an actual identity system. Client-side checks, a hidden URL, and 0% routing are not production access controls. A real trusted boundary must validate identity and preview approval for every candidate path.
      • 
        
    • Only the seven enumerated paths and fixture identities are modeled. Real APIs, callback protocols, token signatures/expiry, membership revocation, session isolation, host routing, and unlisted bypass paths are unverified.
      • 
        
    • Login/callback continuity and unchanged GA attribution are synthetic assertions, not live SSO, real-user migration, or a native authorization proof. No reliability or availability claim is made.
      • 
        
    • IaC N/A: SOURCE read-only lesson requires no Azure resources. C001 runtime/auth/hosting and separate scaffold/deploy approvals are not granted.
      • 
        
    • A-S006 alone does not complete B-S006 or D-S006. Native proof still needs CORE, DATA, and CONTAINER gates and the source acceptance criteria. One stable Kano unit remains A-S006; packet LP-PROFILE is not closed by this lesson.
