Is a dependency failure
a reason to hold?

Validate required connectivity before admitting users. Keep optional outages visible without blindly ejecting healthy capacity.

Objective and preconditions

Source S022 · Parent D-S022 · Gate SOURCE · Candidate candidate-v2.

Database, queue/messaging and service are always required. Choose whether this workload also requires cache. In the optional-cache workload, a declared database fallback makes a cache outage non-gating only while required connectivity succeeds.

This finite model assumes that fallback is suitable for the workload; connectivity alone does not prove its functional correctness, latency or capacity. Do not apply this policy to a real application without measuring those properties.

  • Fixed synthetic clock: 120000 ms. Connected/disconnected/unknown observations: age 5000 ms.
  • Freshness limit: 30000 ms, inclusive. Stale connected evidence: age 30001 ms. Missing evidence has no timestamp.
  • Four dependency checks per run; up to 8 retained runs and 64 configuration changes. Everything stays in memory until reset or reload.
  • Protected existing synthetic capacity: 4 of 4. No real service, traffic, subscription, credentials or network calls.

Conduct the exercise

  1. Disconnect cache with the optional-cache workload. Predict ADMIT and inspect the failed check and fallback assumption.
  2. Switch to cache-required with the same outage. Predict HOLD. Required checks, not a shallow healthy reply, set the gate.
  3. Make database missing, unknown or stale. Compare UNKNOWN readiness with a known FAILURE.
