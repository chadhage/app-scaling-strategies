S010: Cohort feature-flag activation and reversal

A-S010 · D-S010 · SOURCE · one frozen Kano S unit · LP-LEARN

Enable behavior, not a new deployment. Compatible code is already present in one fixed synthetic deployment. Flags are not an authentication boundary.

Objective and preconditions

Keep existing sessions and cart data valid while one stable cohort changes behavior and returns to standard behavior. Learn why flag reversal cannot repair an incompatible state schema or erase earlier failures.

The deployed reader supports config v1 / state v1. Version 2 is a deliberate mismatch fixture. Four synthetic clients (two pilot, two control) start with one cart item. Each successful observed journey adds exactly one item. Events are deterministic, numbered, and bounded to 60 per run; there is no clock, randomness, or real telemetry.

Observe the off baseline.
Enable pilot with config v1, then observe all four journeys.
Revert the flag to off, then observe again. Check the readable verdict.
Try config v2, or inject state v2 after activation and observe. Reverse: earlier failures and incompatible state must remain visible.

No deployment migration is claimed. Even PASS means only that this synthetic flag-continuity exercise passed. It is not native Azure proof, an availability result, a live transition, or an SLA.
