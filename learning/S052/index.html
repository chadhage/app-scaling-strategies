Keep the supported contract; do not fake a required feature

The new frontend is already loaded. Routing propagation may still send its requests to the old backend. Work through four fixed synthetic GET /profile requests and inspect the effective destination of each one.

api-v1 / profile.v1 returns profileId and displayName. api-v2 / profile.v2 also returns timeZone. All fixture profiles are synthetic. A 200 response is not evidence that a required field or feature works.

  1. Start with the supported base profile and mixed routing; send all four requests.
  2. Try optional timeZone: show its absence on old APIs without inventing a value.
  3. Require timeZone, then compare explicit incompatibility with a status-only success claim.
  4. Try missing observations, timeouts and a malformed old response. Compare the retained results.

Four requests per attempt; eight completed attempts retained in memory. No retries, random data, real API calls or credentials. Configuration locks until the attempt finishes.
