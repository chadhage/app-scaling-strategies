Transfer authority, not just the writer route

Fence writer-old at epoch 41 before admitting writer-new at epoch 42. A delayed write or replayed old grant must not regain authority. Keep every acknowledged effect.

One bounded synthetic handoff

  1. Choose an authority fixture and retained-data fixture. Defaults demonstrate the required safe order.
  2. Begin with two acknowledged effects. Transfer authority before probing the replacement and competing stale tokens.
  3. Replay the old grant. Verify all six write observations and the two original acknowledgements.
  4. Check a learning prediction, inspect retained proof, then compare an unsafe or unknown attempt.

The confirmed receipt assumes an atomic authoritative fence; it does not implement one. “Bypassed” deliberately models a broken authority service. “Unavailable” supplies no authoritative receipt: replacement admission is held and stale outcomes are unknown.

Operator controls

Six fixed configurations, six write observations per attempt, six retained attempts. Settings lock at Begin. No arbitrary writer IDs, epochs, payloads, endpoints or clocks.

Synthetic conditions

Reset or reload clears browser memory only. There are no external resources to clean up.

Source and limits

      
README S069: “Fence the previous writer before accepting writes through the replacement.” D-S069: “Only the authorized epoch writes; stale writers are rejected and acknowledged data is retained.”

      
Every receipt, write, fault and effect here is synthetic. No actual database epochs, lease, fencing protocol, concurrent writers, native host or production Node.js 24 behavior is certified. There are no Azure-management calls, accounts, credentials, IaC, deployments, spending, random events or background work.
