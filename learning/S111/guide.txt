OBJECTIVE AND EXACT SOURCE ACCEPTANCE
S111: Single-worker loss during migration: Surviving capacity continues serving
the declared workload.
D-S111: Surviving capacity and state meet the declared contract; worker/process
versus node/region failure is accurately labeled.
A-S111: Lose one worker; distinguish application-worker, node, zone, and region
failures. SOURCE gate; local-synthetic-only authorization.

This portable A slice is not the native source acceptance. D-S111 calls for
termination of one owned application worker under live journeys. Here every
topology, fault, loss, recovery and outcome is fixed fictional teaching DATA ONLY.
Buttons reveal data. They never terminate processes, change resources/networks,
generate load, inject actual faults, or call Azure. No credentials are present.
IaC: N/A, assessed after the genuine assertion RED and before implementation.

OPEN AND OPERATE
Open index.html with model.js, lesson.js and lesson.css beside it. No server,
framework, account, package install or cloud connection is required. The controls
are native keyboard-operable selects and buttons, with visible focus, a skip
link, state-dependent disabled controls and focused validation errors.

The fictional migration overlaps old-v1 and candidate-v2. Demand is 60 requests/s.
Six fixed journey samples must return HTTP 200 within 120 ms, with matching
session/cart/receipt state. Both serving versions must retain all three records.
These are authored samples, not a complete live throughput or availability test.

Authored topology:
  worker-a: old-v1, node-1, zone-1, region-east; only loss target.
  worker-b: old-v1, SAME node-1 and zone-1, region-east; surviving application worker.
  worker-c: candidate-v2, node-2, zone-2, region-east; surviving candidate version.
  worker-d: standby-v1, node-3, zone-3, region-west; unrouted and unmeasured.
Topology labels are not verified Azure placement. The standby cannot certify DR.

WORKED PATHS
1. Positive: choose Surviving capacity and state / Application worker only.
   Begin -> observe baseline -> record fictional loss -> measure survivors.
   Baseline capacity is 120; post-loss observed capacity is 80 versus demand 60.
   Six samples take 70/80/90/100/110/120 ms; all preserve required state.
   The positive result is restricted to this authored application-worker trace.
2. Capacity negative: reset controls (history remains) and select Insufficient
   surviving capacity. Repeat the ordered actions. worker-b/c have 30/10
   requests/s capacity, total 40. Four samples succeed; two return authored 503
   interruptions. Surviving capacity is insufficient, not a successful migration.
3. State negative: choose Candidate receipt state mismatch. Capacity is 80 and
   all responses are HTTP 200, but the last receipt sample has known wrong state.
   Five successes / one interruption; state and workload contract are negative.
4. Unknown: choose Missing candidate observations. worker-b has known capacity
   40 and three successes; worker-c capacity, state and its three journeys are
   missing (null), not zero or healthy. Total observed capacity/state are unknown.
   Three successes / zero known interruptions / three unknown cannot pass.
5. Scope overclaim: use the positive trace with Node, Zone or Region. The workload
   contract stays positive but the scope claim and overall result are negative.
   Only worker-a is absent. Same-node and same-zone worker-b still serves, so
   node-1/zone-1/region-east have not been lost. Node/zone/region outage tolerance
   remains UNVERIFIED even for the positive trace. Losing a fictional app worker
   is not Azure-zone or Azure-region outage proof.
6. Recovery: after any measured path, reveal fictional worker-a return. Fixed
   recovered capacity is 120; six recovered samples succeed with matching state.
   Recovery does not erase earlier interruptions, unknowns or wrong scope claims.
7. Reset restores only current controls. All run inputs, ordered events and
   measured outcomes remain for six bounded rehearsals. Reload deliberately
   clears the session; no persistent browser storage is used.

STRICT GUARDS
Only exact fixture/scope strings and exactly those two begin-input fields pass.
No arbitrary worker ID, address, command, numeric capacity or real fault input.
Actions require explicit baseline -> loss -> measure -> recovery ordering.
Repeated/out-of-order actions, malformed inputs, forged outcomes, changed
history/counters and over-budget runs fail without mutating the last valid state.
The immutable model replays at most 36 ordered events to validate state. Native
form reset is called through HTMLFormElement.prototype, not a shadowable control.
