S016 — Autoscale oscillation

Objective: Apply suitable stabilization so repeated scale-out/scale-in does not repeatedly interrupt users. Compare the same ten-window demand trace with immediate scaling and with stabilization/cooldown.

Preconditions and limits: Two synthetic ready instances initially; each serves 100 requests/second. Target = ceiling(demand / 100), from one to four instances. Scale-out takes one further observed window to become ready. No Azure account, service, server, management access or credentials are used.

Conduct the comparison

  1. Keep the defaults and advance one window, or run the remaining bounded trace. Both lanes sample four synthetic clients per window, not the offered request rate.
  2. At the first low window, the immediate lane removes an instance with a prior high-window continuation. The next high window queues while replacement capacity warms. Two-window down-stabilization avoids these reversals in the alternating trace.
  3. Inspect requested and effective changes, direction reversals, unsafe removals, client budgets and unknowns separately. A PASS is a successful exercise; the immediate lane's deliberately interrupted users are not an uninterrupted result.
  4. Archive/reset. Select the rebound trace with a four-window cooldown: fewer changes still FAIL when cooldown delays needed capacity. Four-window stabilization avoids scaling in during that short trough.
  5. Try missing observations, HTTP 200/state loss, or high demand 360 plus a readiness failure. Earlier failures and unknowns survive later recovery.
Exact fixture rules and interpretation

Alternating: H,L,H,L,H,L,H,L,H,L. Rebound: H,L,H,L,L,L,H,H,H,H. Each window is one synthetic time unit, not an Azure timer. Immediate scaling has no hold. The stabilized lane requires the chosen consecutive low windows before scaling in. Its cooldown starts at the last scale request and holds either direction until the declared interval has elapsed. Pending scale-out must finish or fail before another request.

A removed instance has one unfinished continuation when the previous window's demand exceeds the remaining capacity. Removing it interrupts one of four sampled clients. A sustained low window lets that teaching continuation finish; stabilization does not create a universal drain guarantee. Known queue = max(0, demand − ready × 100). Latency = 80 + ceiling(queue / (ready × 100) × 1000) ms; equality with the budget passes. Incorrect business state interrupts even with HTTP 200. Missing client or capacity observations are null, never zero or success.

PASS requires all ten windows, fewer scale requests and unsafe removals, zero stabilized interruptions/readiness failures, and complete observations in both lanes. Known stabilized failure takes precedence over UNKNOWN, but unknown counts remain. Healthy clients without demonstrated improvement are NOT_DEMONSTRATED. These are bounded teaching constants, not measured platform behavior or a five-nines claim.

Operator controls

Configure before the first window (locked after observation)

Use Tab, Enter and Space. Apply edits before running; the JSON records the active configuration. Observation conditions can change between windows. Forty commands/run and six archived runs/page are hard limits; existing evidence is never silently discarded.
