## Rules the integrity test enforces

- Addenda are `evidence-index-addendum-<n>.json` in the namespace root, numbered consecutively from 1, closed shape (unknown keys are rejected).
- Addendum 1 names `base` (the seal path and its raw SHA-256); every later addendum names `previous` (`name` and raw SHA-256 of the addendum before it).
- Only the closed list `AMENDABLE` can be superseded: `tests\integrity.test.cjs` and `tests\surface.test.cjs`. Production files, sealed evidence, the seal and
  every other test are never amendable (`AMENDMENT_PATH_NOT_ALLOWED`), with or without an addendum.
- Each step names `previousRawSha256` (it must equal the current head of that path, so the sealed bytes cannot be superseded twice) and the exact `rawSha256` that
  replaces them. `applied` means the working file must hold the new bytes. `authorized` means the exact new bytes are pre-approved: the working file may still hold
  the superseded bytes until the edit is made, and nothing else is accepted.
- Every other sealed file keeps its sealed raw and LF-canonical SHA-256. A different change to an amendable file is rejected naming the path and both expected hashes.
- An addendum may also index new evidence files (`evidence`: path and raw SHA-256). Only new files under `evidence\` qualify: never a sealed path, never `evidence\raw`
  (the sealed capture area), never a path listed twice in the chain. Each listed file must stay byte exact. GREEN runs cannot be indexed by the addendum they need, so
  they are commands in this document, not archives.
- The Git raw-byte gate accepts a committed blob only if it is a state the chain ever legitimized (all sealed files committed, or none), and an addendum already
  committed must stay present and byte identical in the working tree.

## Traps

- Never rewrite or re-seal `evidence\seal-*.json`, never edit a committed addendum, never add anything under `evidence\raw` (the integrity test requires UUID run directories there).
- `.gitattributes` is `* -text`: the raw bytes of every file are what is hashed. The `create` and `edit` tools write CRLF; the addendum JSON is LF like the seal.
- The replay scripts need a fresh directory outside the repository and never touch the repository tree. K-C034 files must not be restored into the repository before K-C034 publishes.
- The head of the chain is anchored only by the committed bytes (the Git gate): a new addendum is trusted when it is published, and every later addendum links to it by hash.
