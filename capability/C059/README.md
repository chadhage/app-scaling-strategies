# C059: the core conducting journey, operable with the keyboard and a screen reader

A **synthetic, local-only, offline** H008/H012 fixture on `127.0.0.1` (automatic port, Node built-ins only). One page composes the core conducting journey: **choose** a delivered lesson (the accepted C041 host, read-only) -> **conduct one validated step** with its closed input contract (the accepted C042 contract and engine, read-only, pinned) -> see the **explicit result** -> use the **offered recovery controls** after a typed failure (retry, correct and resubmit, cancel, resume, inspect). It is **not** the approved Node.js 24 LTS / Express / Entra control API, validates no production runtime, verifies no identity, registers no real service and makes no cloud call, no spend and no Azure call. Node `v22` here is test tooling.

## What is and is not claimed (read this first)

- **No real screen reader was run.** NVDA, JAWS and Narrator behaviour is **NOT claimed**. What is verified is the *programmatic* side: ARIA semantics, names, roles, states, the live region, focus management and keyboard operability, by `a11y-check.js` (against a DOM stub and the real DOM in Edge), an independent oracle in the tests, the real accessibility tree (`locator.ariaSnapshot()`, Playwright 1.56.1) and a recorded keyboard traversal in real headless Edge. A screen reader may still announce things differently; that is a separate, manual check this card does not replace.
- The **isolated browser helper allows only GET** (`testing\browser\isolated.cjs`): the real browser **cannot POST**. Submitting the form in Edge therefore fails at the network layer and the page reports the outcome as **UNKNOWN** (no valid answer, so it is not known whether anything was applied), never as success, and offers Retry and Inspect. States that need a POST are reached in Edge through the **GET Inspect** control on steps prepared from Node (committed, in flight, cancelled, interrupted, unknown key). The POST actions themselves (submit, retry, cancel, resume, unsupported action) are proved by `node:test` suites over **real loopback sockets**, by the page tests that drive the real `page.js` against the real C042 engine, and by a **server-produced transcript** (`GET /transcript.json`: the service drives its own POST journey against private instances, a client that disappears, a restart and an explicit resume, and returns what it recorded). Edge re-derives every envelope of that transcript with the page's own rules.
- The lesson **frame content** (accepted C041 lessons A-S001 and A-S003) runs in an opaque-origin sandbox and is **not** covered by these checks: only the host side is (the frame has a name, the focus enters and leaves it, a Close control returns the focus to its invoker).
- C059 does **not** recheck C001 consent (C042's CLI does and reads the live ledger); it binds only `127.0.0.1` and accepts only `--data-dir=<name>` and `--settle-ms=<0 to 60000>`. A data name that is a Windows device name (`nul`, `con`, `com1` ...), ends with a dot or is not `[A-Za-z0-9][A-Za-z0-9._-]{0,31}` is refused before anything is created.

## Run it

```powershell
node capability\C059\server.cjs --settle-ms=20000
```

It prints one JSON line with the exact origin; open it in a browser. Ctrl+C stops it. Routes: `GET /` (page), `/page.js`, `/journey.js`, `/a11y-check.js`, `/styles.css`, the pinned `/c042/contract.js` and `/c041/{accepted-catalog,host-policy,lesson-host}.js`, the pinned lesson assets `/c041-lessons/<A-S001|A-S003>/<file>`, `/scope.json`, `/transcript.json`, `GET /v1/leases`, `POST /v1/steps`, `GET /v1/steps/{key}`, `POST /v1/steps/{key}/{cancel|resume|anything else = UNSUPPORTED_ACTION}`. Every answer carries the strict headers (CSP `default-src 'none'` with `connect-src 'self'` and `frame-src 'self'`, `nosniff`, `no-store`, `Referrer-Policy`, `Permissions-Policy`; lesson assets carry the C041 lesson CSP with `sandbox allow-scripts`).

## The accessibility contract (each rule has its own negative test)

`a11y-check.js` is pure and dependency-free: `check(document, options) -> { ok, findings: [{ code, selector, message }] }`, plus `tabOrder`, `walkTab` (a keyboard-trap detector over injected key presses that ALSO finds a control Tab never reaches, from the markup and not from the focusable set), `unreachable(document, visited)` (the controls a recorded Tab walk did not visit, composite members excepted: the real-Edge run uses it), `checkStyles(css)` and `accessibleName`. The page must pass it after **every** user action (render, choose, open, close, invalid submit, submit, typed failure, retry, correct-and-resubmit, cancel, resume, inspect, start over, a lost answer, a tampered answer, a request that never gets an answer); `tests\checker.test.cjs` proves each rule on a fixture that is valid except for that one defect (`tests\fixtures.cjs`), and the second review's class tests attack the checker with the classes it claims to catch: `tests\negatives.cjs` holds NAMED negative fixtures (K3, K5-K15, V2, V3, X1-X24) and positives (P1-P13) that `tests\checker-reach.test.cjs` runs on the DOM stub and `tests\browser.cjs` runs on the REAL DOM in Edge (with real Tab presses for the unreachable controls). The third review's class tests (`tests\checker-fp.test.cjs`, review N3) pin the two false positives it found and their boundaries: a decorative `<button tabindex="-1">` or `<a href tabindex="-1">` inside an `aria-hidden` subtree is exposed to nobody and needs no Tab stop (P10, P11: no `ARIA_HIDDEN_FOCUSABLE`, `CONTROL_NOT_REACHABLE` or `TABINDEX_NEGATIVE`; `walkTab` and `unreachable()` ignore it), while a TABBABLE control inside `aria-hidden` is still `ARIA_HIDDEN_FOCUSABLE` (X20-X22) and a `tabindex="-1"` control outside it, or inside `aria-hidden="false"`, is still unreachable (K6, K7, X24); `<nav role="tablist">` (P12) and a heading with `role="menuitem"` (P13) are allowed by ARIA in HTML, while `<nav role="button">` (X23) and the other roles outside the table stay `ROLE_MISMATCH`.

| Area | Rule codes |
| --- | --- |
| Names | `NAME_MISSING`, `NAME_MISMATCH` (label in name, also for `aria-labelledby`), `GROUP_NAME_MISSING` (radiogroup, group, region, dialog, tablist, tabpanel), `NAV_NAME`, `LABEL_TARGET_MISSING`, `ARIA_REF_MISSING`, `ID_DUPLICATE`, `ROLE_INVALID` (unknown role), `ROLE_MISMATCH` (a role that does not fit the native element: `button role=heading`, `h2 role=button`, `input role=button`, `a[href] role=heading`; the table covers button, a, h1-h6, input by type, select, textarea, nav, main, ul, ol, li, and follows ARIA in HTML for them (`nav` allows `tablist`, a heading allows `menuitem`); other elements are unconstrained), `STATE_MISSING` (checkbox, radio, switch need `aria-checked`, tab needs `aria-selected`; native checkboxes and radios carry their own state) |
| Document | `DOC_LANG`, `DOC_TITLE`, `ZOOM_BLOCKED`, `H1_COUNT`, `HEADING_ORDER`, `LANDMARK_MAIN` |
| Keyboard | `TABINDEX_POSITIVE`, `FOCUSABLE_NO_ROLE`, `ARIA_HIDDEN_FOCUSABLE` (a control in the Tab order whose element OR any ancestor is `aria-hidden`; a `tabindex="-1"` control there is exposed to nobody and is not reported), `ROVING_TABINDEX` (radio group and tab list), `KEYBOARD_TRAP` (`walkTab`), **`CONTROL_NOT_REACHABLE`** (a shown, enabled control, outside any `aria-hidden` subtree, that is not in the Tab order and is not a member of a composite widget with one roving tab stop) with its cause `TABINDEX_NEGATIVE` (a native control or a control with a tabindex below 0) or `ROLE_NOT_FOCUSABLE` (an interactive role without tabindex: a mouse-only control), `DISABLED_FOCUSABLE` (`disabled` plus a tabindex of 0 or more) |
| Focus | `FOCUS_LOST` (body), `FOCUS_DETACHED` (removed element), `FOCUS_HIDDEN`, `FOCUS_UNNAMED` |
| Form errors | `ERROR_FIELD_UNDESCRIBED` (aria-invalid + aria-describedby the message), `ERROR_SUMMARY_MISSING`, `ERROR_FOCUS` (first invalid field), `ERROR_STALE`, `ERROR_SUMMARY_STALE` |
| Status | `LIVE_REGION_MISSING`, `LIVE_REGION_COUNT` (exactly one polite region, no alert), `LIVE_REGION_OFF` (a status, alert or log role with `aria-live` off or invalid), `LIVE_REGION_HIDDEN` (an announcing region inside `aria-hidden` content; neither counts as THE polite live region), `ANNOUNCEMENT_CONTRADICTS_STATE` (success wording for a state that is not succeeded), `ANNOUNCEMENT_INCOMPLETE` (typed code and every offered action named), `RECOVERY_MISMATCH`, `STATE_AMBIGUOUS`, `COLOUR_ONLY`, `BUSY_NOT_PROGRAMMATIC`, `DISABLED_NOT_PROGRAMMATIC` |
| Styles (`checkStyles`) | `FOCUS_INDICATOR_MISSING`, `REDUCED_MOTION_IGNORED`, `TEXT_CLIPPING_RISK`, `FIXED_FONT_SIZE` |

`checkStyles` works on parsed declarations (comments, `@media (prefers-reduced-motion: reduce | no-preference)` and `@media print` blocks are removed by balanced-brace scanning): an outline counts as removed for `none`, any zero width, `outline-style: none` and a transparent colour (a `box-shadow` ring beside it is accepted); `:focus:not(:focus-visible)` is not a removal; every animated rule (`transition`, `animation`, `scroll-behavior: smooth`) must be covered by a reduced-motion rule that turns it off and names the same selector or `*`; `height` or `max-height` in a font-relative or absolute length with hidden overflow is clipping (not `min-height`, `%` or viewport units); a `px` or `pt` font size outside `@media print` is fixed. **What it cannot check**: it is a heuristic over declarations, not a cascade engine: it does not compute specificity, inheritance, `@import`, custom properties, computed styles or selectors beyond the `:focus` family, and it does not know whether a colour contrasts with its background.

Conventions the checker relies on (documented here, tested): the result section carries `data-outcome` (`none`, `pending`, `validation`, `succeeded`, `rejected`, `unsupported`, `unknown`, `cancelled`, `interrupted`), `data-code` and `data-recovery`; the one live region `#status` carries `data-about` (`ready`, `navigation`, `validation`, `progress`, `result`); error message ids end with `-error`; the error summary is `#error-summary`.

## Keyboard model and the way out of every widget

| Control | Keys |
| --- | --- |
| Whole page | Tab / Shift+Tab in document order (skip link, step links, lesson radios (one stop), Open, Close, key, lease, units, Conduct, then the recovery buttons, Start over); `tabindex` is never positive. **Reachability rule**: every shown, enabled control (a native control, a link with `href`, or an element with an interactive ARIA role) is in the Tab order, or is a member of a composite widget (the radio group, a tab list) that has exactly one tabbable item and is operated with arrow keys; anything else is `CONTROL_NOT_REACHABLE`. The arrow-key operation of the page's own group is proved by `tests\keyboard.test.cjs` and in Edge, not by the static rule |
| Lesson chooser (ARIA radio group) | One tab stop (the chosen radio, or the first); Arrow keys move **and** choose with wrapping; Space chooses the focused radio; Tab leaves the group. No Home/End (not part of the pattern) |
| Buttons, links | Enter (and Space on buttons) activate |
| Lesson frame | Open focuses the lesson heading; Tab enters the frame (the frame has a name); Shift+Tab or **Close the lesson** leaves it and returns the focus to **Open**; there is no dialog and no focus trap |
| Form | Enter in a field submits; an invalid submit moves the focus to the first invalid field |

Focus after every action (always a named, visible, focusable target, never the body or a removed element): render -> the h1; choose -> the radio; open -> the lesson heading; close -> Open; invalid submit -> the first invalid field; submit, retry, cancel, resume and inspect -> the result heading (moved at the start of the request, so no removed button ever held the focus; a user who moves on while waiting is not pulled back when the answer arrives); correct-and-resubmit -> the key field; start over -> the first lesson. While a request is in flight `aria-busy="true"` is set on the result and the form and the Conduct and Start over buttons carry `aria-disabled="true"` (they stay focusable, so the focus is never lost); a second submit is ignored.

## Status announcements

One polite live region (`role="status"`, `aria-live="polite"`) announces **each state change exactly once** (one write per change; the DOM stub logs every write and Edge counts MutationObserver records): the progress ("Working on ...") and then the explicit result for a request (two), a choice, open, close, a validation failure or a start over (one). Every sentence is **re-derived from validated facts and fixed catalogs**, never from server prose (C017 F3): `journey.present()` validates the envelope (C042 `validateResultEnvelope`), the HTTP status against the envelope and the typed code, the outcome against the code, and the offered actions and reason against the catalog; a tampered answer, malformed JSON or a lying status is shown as the **unknown** outcome with the page's own words (`ANSWER_REJECTED`, `NO_VALID_RESPONSE`) and offers Retry and Inspect. **An answer is bound to ITS request** (review F6): the page refuses a perfectly valid envelope of ANOTHER step (`KEY_MISMATCH`: another key, another lease, 9 units), an echo of another input than the one it sent (`INPUT_MISMATCH`), an applied effect that is not its input's (`EFFECT_MISMATCH`) and an attempt count that its own trail contradicts (`ATTEMPTS_MISMATCH`: attempts must equal 1 plus the `resume` records of the trail once a step began, else 0); the page never adopts a key from an answer, so the next Inspect, Cancel or Resume still targets its own step. For Inspect, Cancel and Resume only the key can be bound (after a conflicting resubmit the form holds another input than the stored step). **A null key or a null echo is no exemption** (review N2): the pinned C042 validator allows an envelope whose `idempotencyKey`, `validatedInput` and `inputSha256` are null, so a valid envelope of another step with the three fields nulled used to pass the binding and was announced as success; an answer that CONFIRMS a step (`accepted`: every success, an Inspect of a step, a Cancel) must carry the key of its request (else `KEY_MISMATCH`) and the input it echoes (else `INPUT_MISMATCH`); only a typed refusal may carry neither (a `415`, a `413` or an invalid-JSON answer is produced before the key is known), and a refusal that carries the key of ANOTHER step is still refused as `KEY_MISMATCH`; `tests\bind-null.test.cjs` tries every combination of the three fields (real, null, deleted) on a succeeded, a replayed, an inspected and a cancelled answer of the real engine, the reviewer's probe, a refusal without a key (still shown) and the real page for a submit, an Inspect and a Retry. **A request that is never answered is abandoned** (review F8): `fetch` carries an `AbortSignal`, the page arms one deadline per request (`journey.REQUEST_DEADLINE_MS`, 15 s, cleared on every outcome) and an abort, also while the body is being read, is the typed failure `NO_ANSWER_IN_TIME` ("No answer arrived in time and the request was abandoned, so it is not known whether it was applied"), announced once, with Retry and Inspect offered and the page no longer busy; the tests inject the timers, so no wall clock is involved. `#host-note` (the C041 host's own line, which knows only "mounted" and "nothing mounted") is kept truthful by the page: after a choice or a close it says "A-S001 is chosen and not open" (review F7). A success is announced only for the outcome `succeeded`; a typed failure names its code and every offered recovery action. Outcomes are always text plus a symbol (`✔ ✖ ⊘ ? ■ ⏸`), never colour alone.

## Resource bounds and the refusal rule

ONE write path, `writeAnswer()`, sends every answer. **A refusal is any answer with status 400 and above** (the typed refusals of the service, an engine rejection such as `CAPACITY_EXHAUSTED`, and every answer NODE would give by itself: its `417` for an expectation other than `100-continue` (`server.on('checkExpectation')`), its `400` for a request without `Host` (`requireHostHeader: false`: the handler answers `421`) and `100-continue` (`server.on('checkContinue')`: the interim `100 Continue` is sent when the request STARTS in its lane, never for one that was dropped) are **lane entries**, decided in their turn after the requests before them were answered (review N1); only the parse errors of `clientError` (a typed `400 MALFORMED_REQUEST`, `431 REQUEST_HEADERS_TOO_LARGE` or `408 REQUEST_TIMEOUT`, written and followed by the destroy) are decided at once, outside the lane): it is DECIDED synchronously, at the moment the answer is written, in `decide(socket)`: the connection is marked in a `WeakSet` (`request.socket`, never `response.socket`: a response queued behind another has no socket yet) and every request already waiting behind it is dropped; the answer carries `Connection: close` and the socket is destroyed once the answer is flushed. **A request pipelined behind a refusal never runs** (the controller addition, `orders\_PIPELINING.md`; the first publication was vulnerable: Node parses every pipelined request of one TCP read and emits each `request` before the first answer exists, so a valid `POST /v1/steps` behind any refusal RAN and the client saw only the refusal; RED `run-4`, and `run-6` for the Node-own answers and the HTTP/1.0 framing, both against the published service). Design: (1) the first lines of the request listener drop a request when its connection is marked; (2) the requests of one connection run through a per-socket lane, one at a time, each only after the answer before it has closed (`drain()`), so a request that was dispatched before an asynchronous refusal (invalid JSON, a missing or unknown field, an unsupported schema version, a full lease) exists is still waiting when that refusal drops the queue; (3) every answer that Node would give itself and that is not a parse error takes its place in the SAME lane (`KIND`: an ordinary request, a `100-continue` request, a request whose `Expect` Node cannot honour), so a refusal is only ever decided by the request whose turn it is: everything before it has been answered and everything still queued comes after it (review N1: the `417` used to be decided when the request was PARSED, outside the lane, which dropped the requests BEFORE it). Consequences, stated plainly: a legitimate pipeline is answered in order, one request at a time; the answers after the first refusal are never sent (for a refusal decided in the lane the client receives the answers of ALL earlier requests in order, then the typed refusal, then the connection closes; for a parse error see the limits below); a client that pipelines more than 4 waiting requests loses the connection. `tests\pipelining.test.cjs` proves it with raw sockets, ONE write per case, against the service in a SEPARATE process, for 28 rows (the 19 typed refusals, the answers Node gives itself, a refused request that also asks for an `Upgrade`, and `CONNECT`, which Node drops without any answer) as the first and as the middle request ([refusal][valid submit] and [valid GET][refusal][valid submit]) in BOTH framings (the refusal and the mutation behind it each as HTTP/1.1 or HTTP/1.0: `maxRequestsPerSocket` is not applied to HTTP/1.0 and not advanced by Node's own answers, so the service never relies on it and keeps its own per-socket guard), the same pairs in TWO writes, [valid submit][refusal] (the submit applies), chunked and `Expect: 100-continue` framing, a quota-full engine rejection, a parse error while a request is in flight (the engine executor is held) and the honest pipeline; each case compares the lease ledger, the journal record count and the step with the state before. Behind an HTTP/1.0 request without keep-alive every further byte is data after `Connection: close`: Node reports it through `clientError`, the service answers it with the typed `400` (after the refusal's own answer when that was already decided) and the request behind never reaches a handler. A parse error ends the connection at once: the answer of an earlier request that is still running on it is lost, its effect is not, and a request that is still waiting behind the one in flight never starts. An `Upgrade` header is ignored, as RFC 9110 allows (the request is answered as an ordinary one, never with `101`; Node stops parsing the TCP read at it). The state-full rejection (`STEP_LIMIT_REACHED`, 256 steps) takes the same code path as the quota-full one (status 503) but is not reachable cheaply with the 110 units of capacity, so it has no case of its own. Mutants that must fail a NAMED test and do (`tests\mutants-server.cjs`): the mark inside `decide()`, the queue drop inside `decide()`, the call of `decide()` from the write path and from the parse-error path, the check at the top of the listener, the lane itself, the `close` that starts the next request, `response.socket` instead of `request.socket`, the refusal threshold, and each Node-own route: the `checkExpectation`, `checkContinue` and `clientError` listeners, `requireHostHeader: false`, the typed `431`/`408` table and the interim `100 Continue`; and, for the third review's N1, the lane entry kinds: the `417` decided at parse time again (outside the lane), the branch that answers the `417` entry in its turn (without it the entry is an ordinary request), a branch that answers the wrong entry kind, an entry that forgets its kind and an ordinary request admitted as an unsupported expectation (`tests\lane.test.cjs` and `tests\lane-flood.test.cjs` kill them by name).

**The third review (N1 and N4), measured.** The independent reviewer found that the `417` decided at PARSE time ran outside the lane: with two or more legitimate requests pipelined BEFORE `Expect: nonsense` (`[G][G][X]`, `[G][G][G][X]`, `[G][G][X][G]`, a POST with a body) `decide()` cleared the queue, the earlier request was dropped, Node could not flush the `417` queued behind it and the connection stayed open (still open after the 90 s idle bound that this file states; 128 such sockets of about 150 bytes pinned the 128-connection cap and a legitimate GET got `ECONNRESET`); `[G][X]` was fine. The fix routes the `417` through the lane like `checkContinue` (RED `run-10`; `run-7` is the retained first attempt of the same tests). `tests\lane.test.cjs` puts one to three legitimate requests BEFORE every Node-own refusal (the `417` for a GET and for a POST with a body, a refused `100-continue`, a request without `Host`, the service's own `404`, and the five `clientError` rows) in eight shapes (`[G][X]`, `[G][G][X]`, `[G][G][G][X]`, `[G][G][X][G]`, `[G][G][X][L]`, `[M][G][X]`, `[M][M][X][L]`, `[M][G][X][L]`: G a legitimate GET, M a valid submit, L a valid submit BEHIND the refusal) and four framings (the earlier requests and the refusal each as HTTP/1.1 or HTTP/1.0), against the service in the test process AND in a separate process, ONE write per case. For the rows decided in the lane (HTTP/1.1) the test requires the answers of all earlier requests in order, then the typed refusal with `Connection: close`, the interim `100 Continue` only for the request that started, the server closing the connection (a connection that stays open is a failed assertion), every M before the refusal run exactly once (`attempts` 1) and every L behind it never run. Every other case (an HTTP/1.0 framing, a parse error) must keep the order of the answers it does send, send no answer after a refusal, end with a closed connection, apply no later request and apply an earlier one at most once. `tests\lane-flood.test.cjs` (a structural test: sockets are counted, no duration is asserted) opens 128 sockets that each write `[G][G][Expect: nonsense]` against the service in a separate process: every socket is closed by the server, the server holds no connection and a legitimate GET is answered; a control of 128 x `[G][G][404]` shows the same facts. **A parse error is decided at once, outside the lane**: `[G][G][malformed]` is answered `200`, `400` and closed (the second GET's answer is lost; a probe of `[M][M][malformed][M]` answered `201`, `400`, applied BOTH mutations because Node let the first requests finish before it reported the parse error, and never ran the one behind it, so an earlier effect is not lost but an earlier answer can be); this is the behaviour the retained `run-6` pins (a parse error with a request in flight) and it is not claimed to be in order. **`100 Continue` is sent when the lane STARTS the request, before the Host, Origin, URL, media-type and length checks** (RFC 9110 allows it): a request that is then refused (`415`, `413`, ...) first invites the client to upload its body, which the destroy discards (`[G][doomed POST with Expect: 100-continue]` is answered `200`, `100`, `415`); `tests\lane.test.cjs` asserts the interim count. **The depth bound** (`pipelineDepth`, 4) allows one running and four waiting requests: five GETs in ONE write are all answered in order, six or more are cut (the connection is destroyed at once and the answers still unsent are lost: the reviewer measured one answer for eight GETs; the test asserts fewer answers than requests and a closed connection, not an exact count).

`tests\server.test.cjs` is table-driven over every refusal the service can emit before it reads a body (421, 403, 414, 400 x6, 405 x4, 404 x3, 415, 413). **The refusal flood** (`tests\flood.test.cjs`, review F2 and F4) runs the attacker in **another process** (`tests\attacker.cjs`, 60 sockets, every refusal status, endless chunked bodies) against the service in a child with `--max-old-space-size=48`, and judges it by STRUCTURE and by CONTROLS measured in the SAME run, never by seconds: every attacker socket is closed by the service (a naive keep-alive server never does), no connection remains, a GET is answered after the flood, the bytes the service read stay within a ratio of a bare 400-and-close reference server run in the same test, the child's CPU time per socket stays within a ratio of that reference, and the heap is bounded. A NAIVE keep-alive server fails the same assertions BY NAME (`SOCKETS_NOT_CLOSED_BY_THE_SERVER`; RED `run-5`), and the load loop (`tests\flood-loop.cjs`: CPU burners, 20 runs, five at a time) is archived in `evidence\raw`. The event-loop lag is only REPORTED (a test diagnostic), never asserted. The first publication claimed that each refused socket costs about 50 ms once and that the stall "stops growing as soon as the sockets are closed"; **that was not reproducible**: the independent reviewer measured 20 ms, 12.3 s and 21 s of event-loop lag for 10, 60 and 200 attacker sockets and 490 ms, 11 s and 37 s for the bare reference server, so the cost is the platform's parse of the attacker's first burst and the scheduler, not C059 logic, and it is neither constant per socket nor bounded by a figure. **The 128-connection cap is shared with an attacker**: at 200 sockets a legitimate probe failed. A reconnect storm can stall the single-threaded loop for tens of seconds, and nothing in this fixture prevents it (no rate limit). Bodies are at most 2048 bytes; headers 8192 bytes and 64 fields; at most 128 sockets; a socket that never completes a request line is closed after 5 s, a slow header or body after about 6 s (`connectionsCheckingInterval` is set to 1 s: Node otherwise enforces those timeouts only every 30 s), an idle keep-alive socket after 1 s, any other idle socket after 90 s; every accepted socket is tracked so `closeServer` never waits for a half-open or never-reading peer. There is no authentication, role boundary, TLS, rate limit or multi-process locking: one service owns one journal directory.

## Honest limits

- Programmatic verification only (see the top of this file). The accessible-name computation is simplified to what this page uses; the checker is not a general auditor.
- The DOM stub is a test double (`tests\dom.cjs`): elements, attributes, events with bubbling, focus, the Tab order and the key defaults the page relies on; Edge is the reference for real behaviour, and its Tab traversal, focus indicator and accessibility tree are recorded.
- A reset can discard a typed answer sent to a client that keeps flooding; the typed answers and `Connection: close` are therefore proved with small complete bodies (`tests\server.test.cjs`, `tests\pipelining.test.cjs`), and the flood test asserts the sockets are closed and the service stays responsive.
- The cost of a refusal flood is the platform and the scheduler, not a figure of this service (see "Resource bounds and the refusal rule": 20 ms, 12.3 s and 21 s at 10, 60 and 200 sockets as measured by the reviewer; the bare reference server 490 ms, 11 s and 37 s). The 128-connection cap is shared with an attacker, and a reconnect storm can stall the loop for tens of seconds. No test asserts a duration.
- A pipeline is served one request at a time and ends at the first refusal; the answers behind a refusal are never sent (documented design, not a defect). **What the client receives, measured (review N1 and N4):** for a refusal decided in the lane (the service's own refusals, the `417` for an unknown `Expect`, a refused `100-continue`, a request without `Host`) every EARLIER request is answered in order and then the typed refusal with `Connection: close`, and the server closes the connection (`tests\lane.test.cjs`, in the test process and in a separate process, HTTP/1.1 and HTTP/1.0, one to three legitimate requests before it, with and without a body); for a parse error (`clientError`) the typed `400`, `431` or `408` is written at once and an earlier answer that was not written yet can be lost (`[G][G][malformed]` is answered `200`, `400`), while the effect of an earlier request is not lost and nothing behind it runs; a pipeline of MORE than 4 waiting requests (a sixth request in one write) is cut at the depth bound: the connection is destroyed at once and the answers still unsent are lost (the reviewer measured one answer for eight GETs). **`100 Continue` is sent when the lane starts the request, before the Host, Origin, URL, media-type and length checks** (RFC 9110 allows an interim response before the final one): a request that is refused afterwards (`415`, `413`, ...) has first invited the client to upload its body, which the destroy then discards; the interim answer is never sent for a request that was dropped. Node honours `Expect` only for HTTP/1.1: an `Expect: nonsense` on an HTTP/1.0 request is ignored and answered as an ordinary request. Not probed: a real h2c upgrade, keep-alive negotiation in HTTP/1.0, real signals and a pipeline whose waiting queue is full when the refusal arrives (the refusal then is the connection cut of the depth bound).
- The mutation run applies the mutants it lists (`tests\mutants-*.cjs`, started from the independent reviewer's generator and extended with every statement and condition of the code added by the fixes); a guard that is not listed is not claimed. **Equivalent mutants** (they survive by design; the report `evidence\raw\mutgen-report-N.json` records each with its reason): the two `control` mutants (one in the page group, one in the checker group) that replace a text by itself (they prove that the runner can report a survivor); and three in `tests\mutants-server.cjs`: `ONLY the socket destroy after the flush` (Node itself destroys the socket after a response that says `Connection: close`, at the same moment; the pipelining guard is the mark, not the destroy), `checkContinue` (without the listener Node writes the interim `100 Continue` itself when the response is assigned the socket, a queued response buffers it and a dropped one never sends it, and the lane already runs the requests one at a time: no client can tell the two orders apart) and `closeServer destroying every tracked socket` (`server.closeAllConnections()` on the next line destroys the same sockets).
- The mutation runs use the QUICK selection of the pipelining matrix (`C059_MATRIX=quick`: one framing pair, one shape, 52 of its 224 tests) and of the lane matrix (`tests\lane.test.cjs`: the `417`, the refused `100-continue` and the service's own `404` rows, one framing pair, the other tests of the file): a mutant that keeps connections open would otherwise make every one of its cases wait for the idle bound. The full matrices, all four framing pairs and every shape, run in the green run and in every RED replay. A test process that dies without naming a failing test (the machine is shared) is not a result: the generators run that mutant again. The report is authoritative for the equivalent mutants and their reasons.
- An `Upgrade` header is ignored (RFC 9110 allows it): the request is answered as an ordinary one and Node stops parsing the TCP read at it, so what is pipelined behind it in the same write is dropped without an answer (it never runs). `CONNECT` is dropped by Node without any answer and without a handler. Neither is a refusal of the service; both are listed in the matrix so that nothing behind them runs.
- A parse error (`clientError`) destroys the connection at once: the typed `400`, `431` or `408` is written first, the answer of an earlier request that is still running on the connection is lost, its effect is not. Two writes to a connection the service has already destroyed can be reset by the peer's stack before the refusal is read, so the two-writes cases assert only that the submit never ran and that at most the refusal (and, in HTTP/1.0 framing, the typed `400`) was answered.
- **A CONSISTENT rewrite of the evidence is not detectable** (review F10): the integrity tests detect a flipped README byte, a flipped transcript byte, an edited manifest count, an edited pin and a changed input of an archived run, but a rewrite of an archived input together with a recomputed manifest hash verifies. The namespace has no external anchor: only the git history, the commit and the tag protect the RED archives, the manifests and the tests. The pin and subject tests need the objects of the accepted commits and of `14cefdea` (a shallow clone fails them).
- `checkStyles` is a heuristic (see "The accessibility contract"); the reachability rule cannot see a key handler, so arrow-key operation of a roving group is proved by tests and by Edge, not by the static rule; `ROLE_MISMATCH` knows only the native elements listed in its table (it follows ARIA in HTML for them: `nav` allows `tablist`, a heading allows `menuitem`, review N3). A control inside an `aria-hidden` subtree is exempt from the Tab-order rules (it is exposed to nobody; a TABBABLE one is still `ARIA_HIDDEN_FOCUSABLE`) but not from the naming rules: a nameless one is still `NAME_MISSING`.
- **Not done in this fix** (stated, not claimed; the same list is in the result file): the whole suite in a scratch tree built from `git archive` of the committed blobs, in LF and in CRLF (the pins accept the raw and the LF form of every imported file and the namespace is stored with `-text`, so the risk is low, but it is untested); the flood and resource tests 64 times in an 8-way loop (the archived loop is 20 runs, five at a time, under four CPU burners); a generic aliasing walker over the public returns, a test that the page oracle compares every rendered id, and a seeded fuzz of `validateForm` and `present` with holes, cycles and throwing getters; a parser-based mutation generator over every statement and condition (the campaign is list-based); an audit of every older README sentence against a named test; a bounded retry for a scratch folder that Windows keeps locked.
