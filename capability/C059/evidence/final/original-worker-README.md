# C059: the core conducting journey, operable with the keyboard and a screen reader

A **synthetic, local-only, offline** H008/H012 fixture on `127.0.0.1` (automatic port, Node built-ins only). One page composes the core conducting journey: **choose** a delivered lesson (the accepted C041 host, read-only) -> **conduct one validated step** with its closed input contract (the accepted C042 contract and engine, read-only, pinned) -> see the **explicit result** -> use the **offered recovery controls** after a typed failure (retry, correct and resubmit, cancel, resume, inspect). It is **not** the approved Node.js 24 LTS / Express / Entra control API, validates no production runtime, verifies no identity, registers no real service and makes no cloud call, no spend and no Azure call. Node `v22` here is test tooling.

## What is and is not claimed (read this first)

- **No real screen reader was run.** NVDA, JAWS and Narrator behaviour is **NOT claimed**. What is verified is the *programmatic* side: ARIA semantics, names, roles, states, the live region, focus management and keyboard operability, by `a11y-check.js` (against a DOM stub and the real DOM in Edge), an independent oracle in the tests, the real accessibility tree (`locator.ariaSnapshot()`, Playwright 1.56.1) and a recorded keyboard traversal in real headless Edge. A screen reader may still announce things differently; that is a separate, manual check this card does not replace.
- The **isolated browser helper allows only GET** (`testing\browser\isolated.cjs`): the real browser **cannot POST**. Submitting the form in Edge therefore fails at the network layer and the page reports the outcome as **UNKNOWN** (no valid answer, so it is not known whether anything was applied), never as success, and offers Retry and Inspect. States that need a POST are reached in Edge through the **GET Inspect** control on steps prepared from Node (committed, in flight, cancelled, interrupted, unknown key). The POST actions themselves (submit, retry, cancel, resume, unsupported action) are proved by `node:test` suites over **real loopback sockets**, by the page tests that drive the real `page.js` against the real C042 engine, and by a **server-produced transcript** (`GET /transcript.json`: the service drives its own POST journey against private instances, a client that disappears, a restart and an explicit resume, and returns what it recorded). Edge re-derives every envelope of that transcript with the page's own rules.
- The lesson **frame content** (accepted C041 lessons A-S001 and A-S003) runs in an opaque-origin sandbox and is **not** covered by these checks: only the host side is (the frame has a name, the focus enters and leaves it, a Close control returns the focus to its invoker).
- C059 does **not** recheck C001 consent (C042's CLI does and reads the live ledger); it binds only `127.0.0.1` and accepts only `--data-dir=<name>` and `--settle-ms=<0 to 60000>`. A data name that is a Windows device name (`nul`, `con`, `com1` ...), ends with a dot or is not `[A-Za-z0-9][A-Za-z0-9._-]{0,31}` is refused before anything is created.

## Run it

```powershell
node capability\C059\server.cjs --settle-ms=20000
```

It prints one JSON line with the exact origin; open it in a browser. Ctrl+C stops it. Routes: `GET /` (page), `/page.js`, `/journey.js`, `/a11y-check.js`, `/styles.css`, the pinned `/c042/contract.js` and `/c041/{accepted-catalog,host-policy,lesson-host}.js`, the pinned lesson assets `/c041-lessons/<A-S001|A-S003>/<file>`, `/scope.json`, `/transcript.json`, `GET /v1/leases`, `POST /v1/steps`, `GET /v1/steps/{key}`, `POST /v1/steps/{key}/{cancel|resume|anything else = UNSUPPORTED_ACTION}`. Every answer carries the strict headers (CSP `default-src 'none'` with `connect-src 'self'` and `frame-src 'self'`, `nosniff`, `no-store`, `Referrer-Policy`, `Permissions-Policy`; lesson assets carry the C041 lesson CSP with `sandbox allow-scripts`).

## The accessibility contract (each rule has its own negative test)

`a11y-check.js` is pure and dependency-free: `check(document, options) -> { ok, findings: [{ code, selector, message }] }`, plus `tabOrder`, `walkTab` (a keyboard-trap detector over injected key presses that ALSO finds a control Tab never reaches, from the markup and not from the focusable set), `unreachable(document, visited)` (the controls a recorded Tab walk did not visit, composite members excepted: the real-Edge run uses it), `checkStyles(css)` and `accessibleName`. The page must pass it after **every** user action (render, choose, open, close, invalid submit, submit, typed failure, retry, correct-and-resubmit, cancel, resume, inspect, start over, a lost answer, a tampered answer, a request that never gets an answer); `tests\checker.test.cjs` proves each rule on a fixture that is valid except for that one defect (`tests\fixtures.cjs`), and the second review's class tests attack the checker with the classes it claims to catch: `tests\negatives.cjs` holds NAMED negative fixtures (K3, K5-K15, V2, V3, X1-X24) and positives (P1-P13) that `tests\checker-reach.test.cjs` runs on the DOM stub and `tests\browser.cjs` runs on the REAL DOM in Edge (with real Tab presses for the unreachable controls). The third review's class tests (`tests\checker-fp.test.cjs`, review N3) pin the two false positives it found and their boundaries: a decorative `<button tabindex="-1">` or `<a href tabindex="-1">` inside an `aria-hidden` subtree is exposed to nobody and needs no Tab stop (P10, P11: no `ARIA_HIDDEN_FOCUSABLE`, `CONTROL_NOT_REACHABLE` or `TABINDEX_NEGATIVE`; `walkTab` and `unreachable()` ignore it), while a TABBABLE control inside `aria-hidden` is still `ARIA_HIDDEN_FOCUSABLE` (X20-X22) and a `tabindex="-1"` control outside it, or inside `aria-hidden="false"`, is still unreachable (K6, K7, X24); `<nav role="tablist">` (P12) and a heading with `role="menuitem"` (P13) are allowed by ARIA in HTML, while `<nav role="button">` (X23) and the other roles outside the table stay `ROLE_MISMATCH`.

| Area | Rule codes |
| --- | --- |
| Names | `NAME_MISSING`, `NAME_MISMATCH` (label in name, also for `aria-labelledby`), `GROUP_NAME_MISSING` (radiogroup, group, region, dialog, tablist, tabpanel), `NAV_NAME`, `LABEL_TARGET_MISSING`, `ARIA_REF_MISSING`, `ID_DUPLICATE`, `ROLE_INVALID` (unknown role), `ROLE_MISMATCH` (a role that does not fit the native element: `button role=heading`, `h2 role=button`, `input role=button`, `a[href] role=heading`; the table covers button, a, h1-h6, input by type, select, textarea, nav, main, ul, ol, li, and follows ARIA in HTML for them (`nav` allows `tablist`, a heading allows `menuitem`); other elements are unconstrained), `STATE_MISSING` (checkbox, radio, switch need `aria-checked`, tab needs `aria-selected`; native checkboxes and radios carry their own state) |
| Document | `DOC_LANG`, `DOC_TITLE`, `ZOOM_BLOCKED`, `H1_COUNT`, `HEADING_ORDER`, `LANDMARK_MAIN` |
| Keyboard | `TABINDEX_POSITIVE`, `FOCUSABLE_NO_ROLE`, `ARIA_HIDDEN_FOCUSABLE` (a control in the Tab order whose element OR any ancestor is `aria-hidden`; a `tabindex="-1"` control there is exposed to nobody and is not reported), `ROVING_TABINDEX` (radio group and tab list), `KEYBOARD_TRAP` (`walkTab`), **`CONTROL_NOT_REACHABLE`** (a shown, enabled control, outside any `aria-hidden` subtree, that is not in the Tab order and is not a member of a composite widget with one roving tab stop) with its cause `TABINDEX_NEGATIVE` (a native control or a control with a tabindex below 0) or `ROLE_NOT_FOCUSABLE` (an interactive role without tabindex: a mouse-only control), `DISABLED_FOCUSABLE` (`disabled` plus a tabindex of 0 or more) |
| Focus | `FOCUS_LOST` (body), `FOCUS_DETACHED` (removed element), `FOCUS_HIDDEN`, `FOCUS_UNNAMED` |
| Form errors | `ERROR_FIELD_UNDESCRIBED` (aria-invalid + aria-describedby the message), `ERROR_SUMMARY_MISSING`, `ERROR_FOCUS` (first invalid field), `ERROR_STALE`, `ERROR_SUMMARY_STALE` |
| Status | `LIVE_REGION_MISSING`, `LIVE_REGION_COUNT` (exactly one polite region, no alert), `LIVE_REGION_OFF` (a status, alert or log role with `aria-live` off or invalid), `LIVE_REGION_HIDDEN` (an announcing region inside `aria-hidden` content; neither counts as THE polite live region), `ANNOUNCEMENT_CONTRADICTS_STATE` (success wording for a state that is not succeeded), `ANNOUNCEMENT_INCOMPLETE` (typed code and every offered action named), `RECOVERY_MISMATCH`, `STATE_AMBIGUOUS`, `COLOUR_ONLY`, `BUSY_NOT_PROGRAMMATIC`, `DISABLED_NOT_PROGRAMMATIC` |
| Styles (`checkStyles`) | `FOCUS_INDICATOR_MISSING`, `REDUCED_MOTION_IGNORED`, `TEXT_CLIPPING_RISK`, `FIXED_FONT_SIZE` |

`checkStyles` works on parsed declarations (comments, `@media (prefers-reduced-motion: reduce | no-preference)` and `@media print` blocks are removed by balanced-brace scanning): an outline counts as removed for `none`, any zero width, `outline-style: none` and a transparent colour (a `box-shadow` ring beside it is accepted); `:focus:not(:focus-visible)` is not a removal; every animated rule (`transition`, `animation`, `scroll-behavior: smooth`) must be covered by a reduced-motion rule that turns it off and names the same selector or `*`; `height` or `max-height` in a font-relative or absolute length with hidden overflow is clipping (not `min-height`, `%` or viewport units); a `px` or `pt` font size outside `@media print` is fixed. **What it cannot check**: it is a heuristic over declarations, not a cascade engine: it does not compute specificity, inheritance, `@import`, custom properties, computed styles or selectors beyond the `:focus` family, and it does not know whether a colour contrasts with its background.

Conventions the checker relies on (documented here, tested): the result section carries `data-outcome` (`none`, `pending`, `validation`, `succeeded`, `rejected`, `unsupported`, `unknown`, `cancelled`, `interrupted`), `data-code` and `data-recovery`; the one live region `#status` carries `data-about` (`ready`, `navigation`, `validation`, `progress`, `result`); error message ids end with `-error`; the error summary is `#error-summary`.

## Keyboard model and the way out of every widget

| Control | Keys |
| --- | --- |
| Whole page | Tab / Shift+Tab in document order (skip link, step links, lesson radios (one stop), Open, Close, key, lease, units, Conduct, then the recovery buttons, Start over); `tabindex` is never positive. **Reachability rule**: every shown, enabled control (a native control, a link with `href`, or an element with an interactive ARIA role) is in the Tab order, or is a member of a composite widget (the radio group, a tab list) that has exactly one tabbable item and is operated with arrow keys; anything else is `CONTROL_NOT_REACHABLE`. The arrow-key operation of the page's own group is proved by `tests\keyboard.test.cjs` and in Edge, not by the static rule |
| Lesson chooser (ARIA radio group) | One tab stop (the chosen radio, or the first); Arrow keys move **and** choose with wrapping; Space chooses the focused radio; Tab leaves the group. No Home/End (not part of the pattern) |
| Buttons, links | Enter (and Space on buttons) activate |
| Lesson frame | Open focuses the lesson heading; Tab enters the frame (the frame has a name); Shift+Tab or **Close the lesson** leaves it and returns the focus to **Open**; there is no dialog and no focus trap |
| Form | Enter in a field submits; an invalid submit moves the focus to the first invalid field |

Focus after every action (always a named, visible, focusable target, never the body or a removed element): render -> the h1; choose -> the radio; open -> the lesson heading; close -> Open; invalid submit -> the first invalid field; submit, retry, cancel, resume and inspect -> the result heading (moved at the start of the request, so no removed button ever held the focus; a user who moves on while waiting is not pulled back when the answer arrives); correct-and-resubmit -> the key field; start over -> the first lesson. While a request is in flight `aria-busy="true"` is set on the result and the form and the Conduct and Start over buttons carry `aria-disabled="true"` (they stay focusable, so the focus is never lost); a second submit is ignored.

## Status announcements

One polite live region (`role="status"`, `aria-live="polite"`) announces **each state change exactly once** (one write per change; the DOM stub logs every write and Edge counts MutationObserver records): the progress ("Working on ...") and then the explicit result for a request (two), a choice, open, close, a validation failure or a start over (one). Every sentence is **re-derived from validated facts and fixed catalogs**, never from server prose (C017 F3): `journey.present()` validates the envelope (C042 `validateResultEnvelope`), the HTTP status against the envelope and the typed code, the outcome against the code, and the offered actions and reason against the catalog; a tampered answer, malformed JSON or a lying status is shown as the **unknown** outcome with the page's own words (`ANSWER_REJECTED`, `NO_VALID_RESPONSE`) and offers Retry and Inspect. **An answer is bound to ITS request** (review F6): the page refuses a perfectly valid envelope of ANOTHER step (`KEY_MISMATCH`: another key, another lease, 9 units), an echo of another input than the one it sent (`INPUT_MISMATCH`), an applied effect that is not its input's (`EFFECT_MISMATCH`) and an attempt count that its own trail contradicts (`ATTEMPTS_MISMATCH`: attempts must equal 1 plus the `resume` records of the trail once a step began, else 0); the page never adopts a key from an answer, so the next Inspect, Cancel or Resume still targets its own step. For Inspect, Cancel and Resume only the key can be bound (after a conflicting resubmit the form holds another input than the stored step). **A null key or a null echo is no exemption** (review N2): the pinned C042 validator allows an envelope whose `idempotencyKey`, `validatedInput` and `inputSha256` are null, so a valid envelope of another step with the three fields nulled used to pass the binding and was announced as success; an answer that CONFIRMS a step (`accepted`: every success, an Inspect of a step, a Cancel) must carry the key of its request (else `KEY_MISMATCH`) and the input it echoes (else `INPUT_MISMATCH`); only a typed refusal may carry neither (a `415`, a `413` or an invalid-JSON answer is produced before the key is known), and a refusal that carries the key of ANOTHER step is still refused as `KEY_MISMATCH`; `tests\bind-null.test.cjs` tries every combination of the three fields (real, null, deleted) on a succeeded, a replayed, an inspected and a cancelled answer of the real engine, the reviewer's probe, a refusal without a key (still shown) and the real page for a submit, an Inspect and a Retry. **A request that is never answered is abandoned** (review F8): `fetch` carries an `AbortSignal`, the page arms one deadline per request (`journey.REQUEST_DEADLINE_MS`, 15 s, cleared on every outcome) and an abort, also while the body is being read, is the typed failure `NO_ANSWER_IN_TIME` ("No answer arrived in time and the request was abandoned, so it is not known whether it was applied"), announced once, with Retry and Inspect offered and the page no longer busy; the tests inject the timers, so no wall clock is involved. `#host-note` (the C041 host's own line, which knows only "mounted" and "nothing mounted") is kept truthful by the page: after a choice or a close it says "A-S001 is chosen and not open" (review F7). A success is announced only for the outcome `succeeded`; a typed failure names its code and every offered recovery action. Outcomes are always text plus a symbol (`✔ ✖ ⊘ ? ■ ⏸`), never colour alone.

## Resource bounds and the refusal rule

ONE write path, `writeAnswer()`, sends every answer. **A refusal is any answer with status 400 and above** (the typed refusals of the service, an engine rejection such as `CAPACITY_EXHAUSTED`, and every answer NODE would give by itself: its `417` for an expectation other than `100-continue` (`server.on('checkExpectation')`), its `400` for a request without `Host` (`requireHostHeader: false`: the handler answers `421`) and `100-continue` (`server.on('checkContinue')`: the interim `100 Continue` is sent when the request STARTS in its lane, never for one that was dropped) are **lane entries**, decided in their turn after the requests before them were answered (review N1); only the parse errors of `clientError` (a typed `400 MALFORMED_REQUEST`, `431 REQUEST_HEADERS_TOO_LARGE` or `408 REQUEST_TIMEOUT`, written and followed by the destroy) are decided at once, outside the lane): it is DECIDED synchronously, at the moment the answer is written, in `decide(socket)`: the connection is marked in a `WeakSet` (`request.socket`, never `response.socket`: a response queued behind another has no socket yet) and every request already waiting behind it is dropped; the answer carries `Connection: close` and the socket is destroyed once the answer is flushed. **A request pipelined behind a refusal never runs** (the controller addition, `orders\_PIPELINING.md`; the first publication was vulnerable: Node parses every pipelined request of one TCP read and emits each `request` before the first answer exists, so a valid `POST /v1/steps` behind any refusal RAN and the client saw only the refusal; RED `run-4`, and `run-6` for the Node-own answers and the HTTP/1.0 framing, both against the published service). Design: (1) the first lines of the request listener drop a request when its connection is marked; (2) the requests of one connection run through a per-socket lane, one at a time, each only after the answer before it has closed (`drain()`), so a request that was dispatched before an asynchronous refusal (invalid JSON, a missing or unknown field, an unsupported schema version, a full lease) exists is still waiting when that refusal drops the queue; (3) every answer that Node would give itself and that is not a parse error takes its place in the SAME lane (`KIND`: an ordinary request, a `100-continue` request, a request whose `Expect` Node cannot honour), so a refusal is only ever decided by the request whose turn it is: everything before it has been answered and everything still queued comes after it (review N1: the `417` used to be decided when the request was PARSED, outside the lane, which dropped the requests BEFORE it). Consequences, stated plainly: a legitimate pipeline is answered in order, one request at a time; the answers after the first refusal are never sent (for a refusal decided in the lane the client receives the answers of ALL earlier requests in order, then the typed refusal, then the connection closes; for a parse error see the limits below); a client that pipelines more than 4 waiting requests loses the connection. `tests\pipelining.test.cjs` proves it with raw sockets, ONE write per case, against the service in a SEPARATE process, for 28 rows (the 19 typed refusals, the answers Node gives itself, a refused request that also asks for an `Upgrade`, and `CONNECT`, which Node drops without any answer) as the first and as the middle request ([refusal][valid submit] and [valid GET][refusal][valid submit]) in BOTH framings (the refusal and the mutation behind it each as HTTP/1.1 or HTTP/1.0: `maxRequestsPerSocket` is not applied to HTTP/1.0 and not advanced by Node's own answers, so the service never relies on it and keeps its own per-socket guard), the same pairs in TWO writes, [valid submit][refusal] (the submit applies), chunked and `Expect: 100-continue` framing, a quota-full engine rejection, a parse error while a request is in flight (the engine executor is held) and the honest pipeline; each case compares the lease ledger, the journal record count and the step with the state before. Behind an HTTP/1.0 request without keep-alive every further byte is data after `Connection: close`: Node reports it through `clientError`, the service answers it with the typed `400` (after the refusal's own answer when that was already decided) and the request behind never reaches a handler. A parse error ends the connection at once: the answer of an earlier request that is still running on it is lost, its effect is not, and a request that is still waiting behind the one in flight never starts. An `Upgrade` header is ignored, as RFC 9110 allows (the request is answered as an ordinary one, never with `101`; Node stops parsing the TCP read at it). The state-full rejection (`STEP_LIMIT_REACHED`, 256 steps) takes the same code path as the quota-full one (status 503) but is not reachable cheaply with the 110 units of capacity, so it has no case of its own. Mutants that must fail a NAMED test and do (`tests\mutants-server.cjs`): the mark inside `decide()`, the queue drop inside `decide()`, the call of `decide()` from the write path and from the parse-error path, the check at the top of the listener, the lane itself, the `close` that starts the next request, `response.socket` instead of `request.socket`, the refusal threshold, and each Node-own route: the `checkExpectation`, `checkContinue` and `clientError` listeners, `requireHostHeader: false`, the typed `431`/`408` table and the interim `100 Continue`; and, for the third review's N1, the lane entry kinds: the `417` decided at parse time again (outside the lane), the branch that answers the `417` entry in its turn (without it the entry is an ordinary request), a branch that answers the wrong entry kind, an entry that forgets its kind and an ordinary request admitted as an unsupported expectation (`tests\lane.test.cjs` and `tests\lane-flood.test.cjs` kill them by name). **What waits behind a refusal never runs, for every kind of refusal** (review D1, `tests\victim.test.cjs`, 52 tests, in the test process through the service's own `startLocal({ executor })` hook): connection A holds a step in flight (its executor waits on a gate that the test releases) and connection B sends a first request (one that completes, or a second slow step), a body-less `POST /v1/steps/<A's key>/cancel` (the VICTIM: if it ever ran, the step of A would end cancelled) and a refusal. A parse error (19 rows: every Node-own client error that can be reached, the typed `400` and `431` and, with relaxed timers, `408`) is decided AT ONCE by Node's parser with the victim still waiting behind the first request; a refusal of the lane (29 rows: the 20 rows of `tests\refusal-table.cjs`, the `417` and the request without `Host`, and the refusals decided after a body was read or after `Expect: 100-continue`) is decided in its turn with the victim queued BEHIND it. Each row runs in three shapes: everything in one write after a first request that completes; the same after a slow first step; and the last part in a LATER write, sent only after Node has parsed the earlier requests (the parse count of the connection is the observable condition, never a sleep). The assertions: B's answers in order ending with the typed refusal and `Connection: close`, the connection closed, and, after a barrier (the second step finished, a round trip on a third connection and event-loop turns, never a duration), the step of A still in flight, A's `201`, the step succeeded and never cancelled, and the lease ledger and the journal holding exactly the completed steps. The victim is a named CONTROL where nothing refuses it (it MUST cancel the step of A: A gets 409), and four rows after which Node parses nothing (a declared body that swallows what follows, `Connection: close`, an Upgrade) are named controls that assert exactly that (their answers are not asserted: the server destroys a socket that still has unread bytes and a TCP reset may discard a flushed answer). The mutant that deletes `decide(socket)` from `refuseMalformed()` fails 20 of its 52 tests by assertion (RED `run-17`), all of them parse-error rows, because a lane refusal drops its queue through the other `decide()` call. It tests HTTP/1.1 only: HTTP/1.0 framing and the separate process are the matrices of `tests\pipelining.test.cjs` and `tests\lane.test.cjs`.

`tests\server.test.cjs` is table-driven over every refusal the service can emit before it reads a body (`tests\refusal-table.cjs`: 20 rows, the counts are derived from the table in the figures block: 421, 403, 414, 400 x7, 405 x5, 404 x3, 415, 413; the refusals decided after a body was read are rows of `tests\pipelining-support.cjs`). **The refusal flood** (`tests\flood.test.cjs`, review F2 and F4) runs the attacker in **another process** (`tests\attacker.cjs`, 60 sockets, every refusal status, endless chunked bodies) against the service in a child with `--max-old-space-size=48`, and judges it by STRUCTURE and by CONTROLS measured in the SAME run, never by seconds: every attacker socket is closed by the service (a naive keep-alive server never does), no connection remains, a GET is answered after the flood, the bytes the service read stay within a ratio of a bare 400-and-close reference server run in the same test, the child's CPU time per socket stays within a ratio of that reference, and the heap stays under 32 MB for THIS flood (every first request of it is refused at once; the heap is NOT bounded independently of the connection cap: see the paragraph on pending first requests below). The event-loop lag is only REPORTED (a test diagnostic), never asserted. The first publication claimed that each refused socket costs about 50 ms once and that the stall "stops growing as soon as the sockets are closed"; **that was not reproducible**: the independent reviewer measured 20 ms, 12.3 s and 21 s of event-loop lag for 10, 60 and 200 attacker sockets and 490 ms, 11 s and 37 s for the bare reference server, so the cost is the platform's parse of the attacker's first burst and the scheduler, not C059 logic, and it is neither constant per socket nor bounded by a figure. **The connection cap is shared with an attacker** (it is 32 since the third fix, it was 128): at 200 sockets a legitimate probe failed, and 32 idle sockets deny service to a legitimate client (`tests\pending.test.cjs` holds 128 idle sockets: the server keeps 32 and Node drops the other 96 at accept, every socket accounted for). Bodies are at most 2048 bytes; headers 8192 bytes and 64 fields; at most 32 sockets (`BOUNDS.connections`, read back from the server by `tests\lane-flood.test.cjs` and `tests\pending.test.cjs`); a socket that never completes a request line is closed after 5 s, a slow header or body after about 6 s (`connectionsCheckingInterval` is set to 1 s: Node otherwise enforces those timeouts only every 30 s), an idle keep-alive socket after 1 s, any other idle socket after 90 s; every accepted socket is tracked so `closeServer` never waits for a half-open or never-reading peer. There is no authentication, role boundary, TLS, rate limit or multi-process locking: one service owns one journal directory.

**A pending first request keeps about 6 MB of heap per socket (review Q2, the F24 finding of the previous worker); the heap is bounded by the connection cap times that cost, not by the 48 MB of the flood test.** Node's HTTP parser consumes the socket directly and parses a WHOLE read (up to 64 KB: 3,449 requests of the reviewer's 19-byte `GET /x`, 3,640 of the 18-byte `GET /` that `tests\pending.test.cjs` sends) before any JavaScript can cut the connection, and the parsed requests and responses of that read stay alive until the FIRST request of the socket ends. A JavaScript pre-parse guard cannot work on this Node (the independent reviewer showed that a per-socket emit hook sees no `data` event and that a counting guard never fires). The reviewer measured 5.9 to 6.6 MB of live heap per pending socket (1, 4 and 16 sockets): a child with a 48 MB heap survives 3 such sockets and dies at 8. The cost is PER SOCKET and does not grow with the requests a client sends: everything after the first read of a socket is never parsed (the depth bound destroys the socket); `tests\pending.test.cjs` counts the request events per socket for `[valid POST, held by the executor][64 KB blocks of tiny GETs]` and requires at most one read's worth for one block and for forty, every socket closed, a legitimate GET answered and a 48 MB child alive after three such sockets: never a heap size, never a time. A first request is pending in normal use too (the CLI option `--settle-ms`, up to 60,000 ms, keeps every step pending that long). **Worst case: `BOUNDS.connections` x 6 MB, that is 32 sockets, about 190 MB (the cap was 128, about 0.77 GB, until the third fix; it is one constant, read back from the server by two tests; sockets beyond the cap are dropped by Node at accept).** **Measured at the cap** (`evidence\raw\f24-1.json`, the tool `tests\f24-measure.cjs`, which is NOT in the suite; reproduce with `node capability\C059\tests\f24-measure.cjs 256 32 50000 hold`: the real service in a child with a 256 MB heap, 32 sockets whose first request stays pending, each then sending 64 KB blocks of the cheapest request): 32 sockets accepted, 5.9 MB of live heap per socket, 193.3 MB of live heap and a 266 MB resident set in total, 3,450 requests parsed per socket (a whole read, whatever follows), every socket closed by the depth bound, a legitimate GET answered with 200, and 6.0 MB of live heap after the held steps were released. The independent reviewer measured the same (193.3 MB of live heap, 280 MB resident set at 32 sockets; 6.0 MB per socket at 3 and 4, 5.9 at 8, 16 and 32), so the extrapolation held. The only knob is the cap (8 sockets are about 48 MB, 16 about 96 MB at that per-socket cost): no JavaScript mitigation exists, because the parser consumes the whole read before any JavaScript can cut the connection. This is a limit of the Node HTTP parser that C059 documents and bounds; it holds for every server built on it, and cutting earlier than one read would need a different parser. It was NOT measured at 128 sockets (not to saturate the shared machine): the figure is linear from the 1, 4 and 16 sockets the reviewer measured.
