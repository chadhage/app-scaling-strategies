# C017: reconcile cancellation during an in-flight action, and never fabricate an undo

**Synthetic, local, offline.** One fictional lease (`lease-synthetic-001`, run `synthetic-run-001`, user `user-synthetic-001`) runs ONE action, "stage synthetic capacity": 4 ordered steps of 5 synthetic integer units. A client may cancel it while it is in flight. The server owns the truth and answers every cancel with exactly one of five outcomes, each derived from an append-only journal and never from a claim. This is not the approved Node 24 + Express + Entra service, not a real service, and there is no Azure, cloud, real data or spend; those targets stay unvalidated and unregistered.

## The model in six rules

1. **The journal is the truth.** `journal.cjs` appends hash-chained, versioned lines (C015's canonical digest, flushed on every append). Each step writes an `step-intent` BEFORE it acts and a `step-effect` after. `reconcile.cjs` derives every status, fact and outcome from those entries alone, and `derive()` also checks the journal grammar: a forged decision (for example `COMPENSATED` without compensating entries) makes the whole journal unreadable, which is UNKNOWN, never "cancelled". The reader is a strict-grammar reader, not a canonical-form check and not a repair tool (see "What this does not claim").
2. **Cancel is cooperative.** A cancel received during step *k* waits for that step's boundary (an in-flight step is never reported as cancelled), then the action stops.
3. **Five outcomes, closed.** `CANCELLED_BEFORE_EFFECT` (200, no step had begun), `CANCELLED_PARTIAL` (200, steps 1..k STAND and remain, steps k+1.. were NOT run, nothing was undone), `CANCEL_TOO_LATE` (**409**, the action had completed, all effects stand, the cancel was not effective), `COMPENSATED` (200, only when journaled compensating steps ran in reverse order as their own entries with their own negative effects and 0 units stand; a failed compensation is `CANCELLED_PARTIAL` with `compensation: FAILED` and the failing step named), `CANCEL_UNKNOWN` (**503**, a crash or an unreadable journal; facts are `null` rather than empty lists).
4. **Idempotent and single-decision.** A command key is bound to one canonical command; the same key and command replays the journaled answer (also after a restart and a newer epoch), a different command under it is `IDEMPOTENCY_CONFLICT`. Only one cancel is decided per action (`CANCEL_IN_PROGRESS`, `ALREADY_TERMINAL`).
5. **Attribution.** Every command names lease, run, user, epoch and action; answers carry the server's own. Another lease, run, user or action, and a stale or future epoch, are typed failures (`UNKNOWN_*`, `STALE_EPOCH`, `FUTURE_EPOCH`) with allowed recovery actions (`reinspect`, `correct-closed-command`, `confirm-operator-review`, `stop`, `retry-identical`), `effectClaimed: false` and no journal write. The journal is bound to the same closed identity: `derive()` refuses an `action-accepted` entry that names another lease, run or user (a valid digest chain of a foreign run is UNKNOWN, never answered with the foreign identity).
6. **A restart tells the truth.** Opening a journal appends a `boot`. An action that was live at a crash is `INTERRUPTED` (never cancelled, never completed); an intent without an effect is an UNKNOWN step; a cancel that raced the crash replays as `CANCEL_UNKNOWN`. Reconciliation is an explicit `reconcile` command that settles the facts (`INTERRUPTED_KNOWN`, `INTERRUPTED_UNKNOWN`, `CANCEL_UNKNOWN`) and still never claims cancelled or completed.

## Run it locally

```powershell
node capability\C017\cli.cjs                      # steps paced 1500 ms, journal in capability\C017\state
node capability\C017\cli.cjs --step-delay-ms=300 --hold-in-step=3   # rehearse a crash: step 3 never finishes; kill the process, start again, open the page
```

The CLI rechecks C001 consent (the pattern of C020), binds **only `127.0.0.1` on an automatic port**, prints the exact URL and PID, and accepts no host, port, identity or outcome override (`--dir` must stay inside `capability\C017`). Stop with Ctrl+C, SIGTERM, the exact word `stop` on stdin, or the TTL (`--ttl-ms`, default 10 minutes). The page has Start, Cancel (with an optional compensation checkbox), Reconcile and Refresh: native buttons, so Tab, Enter and Space operate them.

## Browser observation and its limit

The shared isolated helper (`openIsolatedLoopback`) forwards only same-origin GET/HEAD and **blocks every write**, so the browser can never deliver a POST. `tests\browser.cjs` therefore (a) presses Tab and Enter on the page's own Cancel control and observes that a blocked request is reported as "not delivered … UNKNOWN: nothing is claimed as cancelled, stopped, started or undone", that the server journal holds no cancel, and that the retry would reuse the same key; (b) lets a Node client POST the cancel, compensation, too-late and reconcile commands and observes the page showing exactly the server's statement through GET (the DOM text equals the journal-proven statement); (c) observes a restarted interrupted action and a tampered journal. Six fresh Edge sessions run: in-flight, compensated, too late, interrupted, unreadable and FORGED. The forged session answers the page with a served GET only (the helper blocks POST): a loopback test double proxies the real server and lies about `/api/state` (it claims `COMPENSATED` while steps 1 and 2 STAND); real Edge must show the typed refusal "Answer rejected: the server's state view contradicts its own facts (...). No cancellation, undo or completion is claimed.", list nothing and leave every command button disabled. Forged POST answers (reconcile, typed failure, start, cancel) cannot be delivered through the helper: they are proved with the real `page.js` under the DOM stub (`page-forged-*.test.cjs`, `page-property.test.cjs`), a limit stated here and not hidden. After each session, the rendered element ids are unique and the journal numbering is the exact delivered sequence (L-0118). `evidence\browser-observation.json` (first publication, immutable) and `evidence\browser-observation-02.json` (final bytes, captured last with `$env:CAPTURE_BROWSER_EVIDENCE='browser-observation-02'`) record the DOM text, Edge's actual version, SHA-256 and Microsoft signature (the suite asserts signature and major 156, never an equality pin on the build). Closing an isolated Edge session is slow on a loaded machine (30 to 90 s per session observed, also against the first-publication code), so a full run can take several minutes. The key of an undelivered cancel is held in page memory so a retry reuses it; a reload loses it, which is safe because the server decides once per action and the reloaded page shows the journal-derived outcome.

## Resource and shutdown bounds (L-0111 to L-0113, L-0120)

One request per connection (`Connection: close`), 2 KB body, 8 KB headers of at most 32 lines (a 33rd header line is a parse error that Node reports and the server answers with the typed 431 `HEADERS_TOO_LARGE`: `limits.test.cjs`, G102), a 64-connection cap (`maxConnections`: a surplus connection is dropped by the server itself, observed on Node's own `drop` event in `limits.test.cjs`, G103), 5 s request and 30 s idle timeouts, a state view capped at the last 48 journal entries, a 256 KB journal that refuses new actions (`JOURNAL_FULL`, 48 KB reserved so a live action can always be cancelled) instead of becoming unreadable, and every accepted socket tracked so shutdown cannot hang. **Close after every answer (L-0120, L-0132, F11, F12, F23):** the ONE central `send()` closes the connection after the answer is flushed, after a bounded drain (at most 32 KB more request bytes or 1 s, and only while fewer than 4 connections of the PROCESS are draining: the surplus is closed right after its answer, so the bound is per process and not per connection), for every answer the server produces except the bodiless 408 that Node itself writes for a request or header timeout (Node destroys that connection at once; `resources.test.cjs` "slow headers and slow bodies are cut off by the request timeout"). That includes the answers Node used to give ITSELF, which bypassed the central path in the first fix: an unknown `Expect` header (`checkExpectation`, typed 417 `EXPECTATION_FAILED`), `Expect: 100-continue` (`checkContinue`: the interim 100 is sent only when the request is about to be read, so a refusal never invites an upload), a request without a `Host` header (`requireHostHeader` is off, so it reaches the handler and gets the typed 403) and a request Node cannot parse (`clientError`: typed 400 `MALFORMED_REQUEST` or 431 `HEADERS_TOO_LARGE`, then the socket is destroyed). There is no `upgrade` or `connect` listener: Node treats an `Upgrade` request without a listener as an ordinary request (it is answered and the connection closed like any other: `refusals-node.cjs`) and destroys a `CONNECT` without an answer. Not probed: HTTP/2, h2c upgrade, a real signal or a redirected profile folder. **One request per connection, in every HTTP version (F12):** the first line of every handler marks `request.socket` in a `WeakSet` (never `response.socket`, which is null for a response queued behind another) and a request on a marked socket is never run and never answered, and a connection that leaves MORE THAN 8 of them behind its first request is DESTROYED (`MAX_DROPPED`, F24 of the third independent review: Node's parser builds a request and a response object for every request it reads, and because nothing was ever written for the dropped ones nothing slowed the socket down, so a flood pipelined behind a PENDING first request, a valid cancel waiting for its step boundary, was retained at about 1.8 KB per request (the reviewer's measurement) until a 48 MB-heap server hung or aborted with exit 134 (also observed here: the RED run of the published second fix died with exit 134 within seconds); ## The page re-derives everything (F3, F8, L-0139)

`page.js` never prints server prose. Every `/api/state` view and every answer is checked by `contract.js` before anything is shown: `viewCheck` (identity, epoch, journal window with a closed list of entry types, steps, lists, standing units, status, cancel summary and reconciliation must agree, the cancel summary passes the same `claimCheck` as a cancel answer, and the JOURNAL PANE is replayed, F13: the window is run through the very same state machine the server derives with (`contract.js` `ledger.derive`, the code `reconcile.cjs` imports) from the first `action-accepted` line of the window on, every line must have exactly the closed fields of its type and be a legal next step, and the action it leads to must equal the action the view claims, key order aside; lines of an earlier action whose start is not in the window cannot be re-derived and are counted as "not shown", never displayed; a view without an action may carry only `boot` lines), `claimCheck` (cancel answers), `reconcileCheck` (closed determination, facts that partition the steps, determination consistent with the unknown steps), `startCheck` and `failureCheck` (the reason and allowed actions of a typed failure are the closed table's, never the answer's). Wording is re-derived from the facts (`statementOf`, `describeDetermination`) or taken from the closed table. An answer that fails is replaced by "Answer rejected: the server's <kind> contradicts its own facts (<fixed sentences>). No cancellation, undo or completion is claimed.", a refused view empties the page and disables every command, a rejected or unrecognized answer keeps the cancel key so a retry stays idempotent, and `showAnswer()` runs inside the same guard as the request (a malformed start answer no longer leaves the buttons disabled). The server's own 500 is now a typed failure of the closed table (`INTERNAL`). ## What this does not claim

No power-loss durability (a regular file is flushed; the directory is not), no tamper-proofing (the chain and grammar detect inconsistency; a consistent rewrite of a whole valid journal is undetectable), no authentication or authorization (the fictional identity is a closed constant; the journal is bound to it, but nobody proves who the client is), no multi-process or multi-lease operation, no production Node 24 / Express / Entra validation. Journal rotation is an operator action. `--hold-before-step` and `--hold-in-step` are rehearsal flags for crash drills, not features of a service.

**Scope of the journal reader (F7).** `journal.cjs` enforces a strict line grammar and the digest chain; it does NOT enforce a canonical byte form and never repairs. A byte-order mark, CRLF endings, padded lines, reordered keys, a duplicated key (the last one wins) and `2.0` for `2` parse to the same logical record and are accepted while the record and its digest agree (`journal-forms.test.cjs` characterizes this); a changed value, a swapped or dropped line, an unknown field and a torn tail are unreadable, and nothing is repaired. The first-publication header comment claimed that any irregularity makes the journal unreadable; that was wrong and is corrected.

**Limits and mechanism limits, stated and not fixed** (reasons are the cost of a fix against what it would protect in a synthetic, loopback-only fixture; none of them lets the engine, the journal, an answer or the page claim a cancellation, undo or completion the journal does not prove):

| Limit | What happens | Why it is left |
| --- | --- | --- |
| F9: import pins | `imports.test.cjs` and `anchor.cjs` detect a changed pinned file, a changed transitive file and an extra static `require` of an unpinned namespace; a LAZY dynamic `require` of an unpinned namespace inside a function that never runs at load is not detected, and a bundle whose `imports.json` pins were re-signed is caught only by `anchor.cjs` against git, not by the in-namespace test | a static scan cannot see a computed require; closing it needs a runtime hook, which would be new production code for a case that needs a malicious committer |
| F10(a): journal capacity | any local client can fill the 256 KB journal in about 82 start, cancel and compensate cycles; every later start is a typed 503 `JOURNAL_FULL` until an operator rotates it (the view stays readable and the 48 KB reserve keeps the last live action cancellable) | the bound is the point (no unbounded growth); rotation is an operator action by design and there is no authentication to ration clients |
| F10(b): silent connections | 64 silent TCP connections lock a legitimate client out until the 5 s request timeout, and can be renewed | a connection cap is what protects memory; per-client fairness needs a client identity this loopback fixture does not have |
| F10(c): cancel on an interrupted action | a cancel with a NEW key on an INTERRUPTED action is answered 503 `CANCEL_UNKNOWN` without being journaled, so that key is not bound and may later be used for a different command; it never claims anything | journaling it would make an unsettled action carry a decision-less request that `derive()` must then treat as raced; the only way out is the explicit `reconcile` command, which is what the answer says |
| oversize bodies (F18, F23) | a client that streams an oversize body in 8 KB blocks as fast as it can may be reset after about 24 KB with no typed answer (also on both earlier publications); under attack the per-process drain budget (4 connections at a time, 32 KB each) can be exhausted and a surplus uploader is reset right after its answer was written; N attackers still cost N first socket reads (64 KB each) before their connection is cut, so the stall grows with N inside the 64-connection cap (the reviewer measured 3.7 s of event-loop lag at 40 concurrent attackers with the first fix's 128 KB-per-connection drain; with the per-process drain budget of this fix his cross-process measurements on a loaded machine were 3.0 s at 10 sockets (the 413 row) and 4.9 s at 40 sockets (the 403 row), against 1.7 s and 2.1 s for the first fix measured earlier on a quieter machine, so there is NO same-time comparison: this README does NOT claim that the per-process budget or the smaller bound lower the stall, and does not claim the opposite either; the first read per attacker remains; what the tests DO assert is structural: every abusive connection is closed by the server after a bounded number of bytes read) | the price of cutting an endless body at once; a global admission limit would need a client identity this loopback fixture does not have |
| parse errors and pipelining | a request Node cannot parse destroys the connection: when it follows a VALID request the answer of that first request can be lost (the idempotency key makes a retry safe); a request pipelined behind the first one is never answered (an HTTP/1.1 client sees a closed connection, no 503) | the alternative is to keep parsing a connection that already misbehaved |
| a flood behind a pending first request (F24) | the ninth request behind the first one destroys the connection, but the rest of the single socket read that carried it (at most 64 KB: 3,600 requests of 18 bytes) is still parsed, because the parser builds the request and response objects before any handler runs; every object is released with the socket, and the first request still runs and is answered if its socket is still there (otherwise an idempotent retry with its key returns the outcome). The engine decides one cancel per action and answers a second cancel with another key `CANCEL_IN_PROGRESS` at once (`server.test.cjs`), so few first requests can be pending at a time; that a first request whose body is still arriving can have nothing parsed behind it is HTTP framing, reasoned and not tested. MEASURED after the last edit (scratch probe, `evidence\by-hand-04\`, a pending first request and a 48 MB-heap child): 4, 8 and 16 connections of the 50-byte request hold (65,310 to 65,536 bytes read per connection, heap +3 MB), but 32 of them, 16 of the 18-byte request and 64 of either ABORT the child with exit 134, so the bound is per connection and `pending-flood-process.test.cjs`, which uses 4 connections of 50,000 requests each, does not prove the many-connection case (the first fix aborts at the same counts, same-run comparison in `evidence\by-hand-04\results.json`; item 7(a) of the third fix cycle) | no listener can run before the parser has built the objects; pausing the socket was rejected (a paused socket cannot see its peer close); a bound on the work per read needs the parser to be fed in slices, which is not a small edit of a file that every capture pins (item 7(a)) |
| the 33rd header line (G102) | a request with more than 32 header lines is a parse error that Node v22 reports and the server answers with the typed 431; this is a behaviour of the Node version of the run (older versions dropped the excess headers instead), and `limits.test.cjs` pins what this Node does | the limit is Node's, the test proves the line that sets it |
| wall-clock guards that remain (F25) | `flood-structural.test.cjs` gives its attackers a 12 s cap, waits at most 30 s for the server's close log and 20 s for a polite close, and the older in-process tests wait on gates and the engine with `support.cjs` `withTimeout` (8 s): a machine stalled for longer than that could fail them without any behaviour failing; none of them failed in any loop or capture of this cycle | converting them is test-tooling work that touches the files every capture pins; the helpers the F25 finding named (`child.cjs`, `pipelining.cjs`) carry no deadline any more |
| not-JSON bodies | a delivered body that is not JSON is reported by the page as "The server is not reachable" (state) or "The request was not delivered or its answer was lost" (answer): a cut-short transfer cannot be told from it; every JSON shape the checks cannot read is refused as such ("Answer rejected: ...") and the checks never throw (F15) | the two cases are indistinguishable from the client |
| window prefix (F13) | lines of an earlier action whose `action-accepted` is not inside the 48-line window cannot be re-derived: they are counted ("N earlier entries are not shown") and never displayed; a lying server can still add or reorder `boot` lines after a settled action (they cannot change a settled action) | showing unverified lines would repeat F13; verifying them needs the whole journal, which the 48-entry cap exists to avoid sending |
| old time-bound bytes of the two chunked tests (F22) | the first fix's `chunked.test.cjs` and `chunked-process.test.cjs` (absolute 1.5 s and 3.2 s bounds) are no longer part of the suite; their bytes are retained only as the pinned evidence of `fix-chunked-process-*`, whose replay serves them under the live names; `fix-red.cjs verify-green-all` skips that group (load-sensitive by construction) and `fix-red.cjs verify-green chunked-process` runs it anyway | the rewrite has its own retained RED (`fix-chunked-structural-*`) and its own loops |
| typed 500 (F21) | `journalWritten: false` in the typed 500 means "this request wrote no journal entry it can account for"; after an exception in the middle of an append the engine marks the journal UNREADABLE and the next answer says so | changing the field to "unknown" breaks the closed table that four retained tests and the page check pin |
| browser | the helper blocks POST: forged POST answers are proved under the DOM stub, forged GET views in real Edge | the helper is shared and may not be edited |
