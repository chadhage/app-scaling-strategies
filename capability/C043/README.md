# C043: execute a bounded preset automatically through the same validated steps as manual operation

A **synthetic, local-only, offline** H008 fixture on `127.0.0.1` (automatic port, Node built-ins only). A *preset* is a declared, versioned, closed-contract sequence of N inputs of the accepted C042 step (`reserve-capacity`, synthetic integer units, two fictional leases) with explicit bounds: maximum steps, maximum duration on an **injected clock** and maximum synthetic units. It is **not the approved Node.js 24 LTS / Express / App Service Linux control API**: it validates no production runtime, verifies no identity, registers no real service and makes no cloud call, no spend and no Azure call. Node `v22` here is test tooling. C017 (reconciliation) is **not implemented**: cancellation is explicit and never an undo; effects of completed steps stand.

Gate C042 (one validated step, typed envelope, journal, recovery controls) is accepted and imported **read-only and pinned** (`imports.json`: raw, LF and git-blob SHA-256 plus commit and tag, recomputed against git by `tests\surface.test.cjs`). C043 adds no step logic: `runner.cjs` calls the same step service (`engine.submit`, and for recovery `inspect`, `resume`, `cancel`) that the C042 server calls for a manual request.

## Run it

```powershell
node capability\C043\server.cjs --data-dir=demo --settle-ms=20000
```

The CLI rechecks current C001 local-probe consent (`approvals.C001`, read-only), binds only `127.0.0.1` on an automatically assigned port, prints one JSON line with the origin and process ID and accepts **only** `--data-dir=<name>` (two journals under `capability\C043\data\<name>\steps` and `\runs`, git-ignored; without it both are in memory) and `--settle-ms=<0 to 60000>` (how long the fictional work of each step takes, so a step stays in flight long enough to cancel, and so that the duration bound can be seen with the real monotonic clock). Directory names are closed: Windows device names (`nul`, `con`, `prn`, `aux`, `com1` to `com9`, `lpt1` to `lpt9`, also with an extension), trailing dots and trailing spaces are refused before anything is created (C042 F5). No host, port, identity or deployment override exists.

| Route | Meaning |
| --- | --- |
| `GET /v1/presets` | the declared presets (a closed, versioned catalog the page validates) |
| `POST /v1/presets` | run a preset (`application/json`, at most 2048 bytes; the body IS the preset) |
| `GET /v1/presets/{key}` | inspect (read-only; 202 while it runs) |
| `POST /v1/presets/{key}/cancel` | cancel explicitly (also the step in flight, through the step service) |
| `POST /v1/presets/{key}/resume` | continue an interrupted preset at its first unacknowledged step |
| `POST /v1/presets/{key}/{anything else}` | typed refusal `UNSUPPORTED_ACTION` (no undo, rollback or release) |
| `GET /v1/leases`, `GET /v1/journal` | the step ledger; journal health including every discarded tail |
| `GET /`, `/page.js`, `/contract.js`, `/validate.js`, `/envelope.js`, `/verify.js`, `/c042-contract.js`, `/styles.css`, `/scope.json`, `/transcript.json` | page, the accepted C042 contract file the page validates with, scope record, server-produced transcript |

## The preset contract `C043-preset/1`

Closed: exactly `schemaVersion` (1), `preset` (a name), `idempotencyKey` (the run key, 8 to 64 characters), `bounds` (`maxSteps` 1 to 8, `maxDurationMs` 1 to 60000, `maxUnits` 1 to 80) and `steps` (1 to 8 inputs of the C042 contract, each with its own idempotency key). The reader is the C042 strict reader (duplicate fields also through escapes, `__proto__`, `constructor`, `prototype`, unsafe numbers, depth, string length, BOM, invalid UTF-8) and **every step is validated by the accepted C042 validator; the frozen output of that validator is what the step service receives** (an object source is serialised and read again, so accessors and later mutation cannot matter). An invalid preset (unknown version, unknown key, too many steps, an invalid step in ANY position, a duplicated step key, a forbidden key) is a typed failure with C042's recovery action `correct-and-resubmit` and **no call of any step function, no journal entry and an unused key**. `maxSteps` and `maxUnits` are decidable from the declaration, so exceeding them is `PRESET_BOUND_EXCEEDED` before the first effect (all steps listed as not run). The duration is measured by the injected clock **between steps and after the last one**; a step in flight is never preempted (a limit, see below).

## Honest behaviour

A run ends in exactly one state and the answer (`C043-preset-result/1`, validated by `envelope.js`, the same file the page loads) lists, from facts, `steps` (per step: `succeeded`, `replayed` (applied earlier, one effect), `failed`, `unknown`, `interrupted`, `cancelled`, `running` or `not-run`), `ran`, `notRun`, `effects` that stand (with units and reserved-after) and `usage`.

| run state | outcome (C035 class) | meaning |
| --- | --- | --- |
| `completed` | `succeeded` (COMPLETED) | every step succeeded within the bounds |
| `stopped` | `failed` (FAILED) | the first refused step stopped it (`PRESET_STEP_FAILED`, details name the step and its C042 code); later steps never called |
| `bounded` | `bound-exceeded` (FAILED) | the duration bound passed (`PRESET_BOUND_EXCEEDED`, `bound` shows limit and observed) |
| `cancelled` | `cancelled` (CANCELLED) | explicit; the step in flight was cancelled through the step service; never a success |
| `interrupted` | `interrupted` or `unknown` | begun, no terminal record (a restart, an interrupted step, an unconfirmed write); never resumed automatically |
| `running` | `unknown` | in flight |

Nothing is undone: effects of completed steps stand and the answer says so. HTTP 2xx means `accepted` (201 only when this request applied an effect, 202 while running); every other answer is non-2xx.

- **Idempotency**: the run key plus the SHA-256 of the validated preset identify the run. The same preset again (also in parallel) joins the run in flight or returns the recorded result (`replayed: true`, no step called again, one set of effects); another preset under the key is `IDEMPOTENCY_KEY_CONFLICT` and the answer shows the preset that owns the key.
- **Restart**: the preset journal replays; a run with no terminal record is `interrupted` until an explicit resume. Resume first asks the step service what it already knows (`inspect`): a step it already committed is acknowledged without a call, an interrupted one is resumed through the step service, one never begun is submitted; **an acknowledged step is never called again**. The crash window (the effect landed, its acknowledgement did not) is reported as an unconfirmed `interrupted` step until resume reconciles it.
- **Recovery controls**: exactly the actions that work in the state (`retry`, `correct-and-resubmit`, `cancel`, `resume`, `inspect`); an interrupted run whose steps all succeeded does not offer `cancel`; a run that the step service contradicts offers only `correct-and-resubmit` and `inspect` (the preset journal says it ended; a new key replays the confirmed steps and resume of that new run finishes the rest); any other action is `ACTION_NOT_ALLOWED` or `UNSUPPORTED_ACTION`, repeating what is allowed.

## Typed codes

`contract.js` is the closed catalog; the input, transport, conflict and unsupported codes are the accepted C042 entries unchanged (a test compares them). New: `UNSUPPORTED_PRESET_VERSION` (422), `TOO_MANY_STEPS`, `DUPLICATE_STEP_KEY` (400), `PRESET_BOUND_EXCEEDED`, `PRESET_STEP_FAILED`, `PRESET_CANCELLED`, `PRESET_INTERRUPTED`, `PRESET_IN_FLIGHT` (409), `PRESET_UNCONFIRMED`, `PRESET_STEP_SERVICE_DISAGREES` (the step service does not confirm an acknowledged step, see the review fixes), `RUN_LIMIT_REACHED`, `RUN_JOURNAL_UNCERTAIN`, `RUN_JOURNAL_UNAVAILABLE` (503), `RUN_NOT_FOUND` (404), and the transport refusals for what Node would answer itself: `EXPECTATION_FAILED` (417), `MALFORMED_REQUEST` (400), `HEADERS_TOO_LARGE` (431), `REQUEST_TIMEOUT` (408).

## Persistence and what it can and cannot detect

Two append-only, hash-chained JSON Lines journals: the C042 step journal (the truth about effects) and the preset journal (`runlog.cjs`: `begin`, `start`, `step` acknowledgement, `resume`, `cancel`, `end`). Each preset-journal line carries the SHA-256 of the previous line **and a check of its own content**, so even an edit of the last line is detected. `tests\journal.test.cjs` flips **every byte** of a persisted journal four ways (about 10,000 flips): each is a typed `JOURNAL_CORRUPT` except a flip of the final newline, which turns the last record into an unterminated tail; that tail is discarded, truncated **and reported** (`GET /v1/journal` `discardedTailBytes`; C042 F2 asked for exactly this) and never silent. Replay cannot detect a journal cut at a record boundary or a forgery that re-chains every line: those are tamper-evident only with an **external anchor** (a test shows the truncated journal replays as a shorter valid one). The step journal inherits C042's F2 behaviour unchanged (its final-newline flip drops the last record; the count is `stepJournalDiscardedTailBytes`). What the first publication claimed here was false and is now implemented: the preset layer checks EVERY acknowledged step (not only the pending one) against the step service whenever it answers about a run it is not driving (its ledger, and in the production composition its own per-step answer), and a step the step service does not hold as committed with the same effect makes the answer `PRESET_STEP_SERVICE_DISAGREES`, never `completed` (details under the review fixes). The preset journal itself is never rewritten.

The first publication (`kanban/C043/88fd6b086069`) was rejected by an independent review on three majors (C043 F1 to F3) and four minors (F4 to F7); the specification of the fixes is `C043-review-fixes.feature` (`C043.feature` stays as published). - **C043 F1, pipelining** (`tests\pipelining.test.cjs`, `tests\pipelining-process.test.cjs`, `tests\pipe-support.cjs`): Node parses every pipelined request of one TCP read before the first answer is finished, so the old server ran a valid POST pipelined behind a refusal (the ledger went 0 to 15 units) although the client only saw the refusal. Now the ONE central `send()` marks the connection (a `WeakSet` keyed by `request.socket`, never `response.socket`) at the moment a refusal is decided (any non-2xx answer, or a body that was not read), and the requests of one connection run strictly one after the other (a per-connection queue: a request starts when the answer of the previous one is complete), so even a refusal decided after an await stops everything behind it. A request on a marked connection is dropped without effect (the socket is destroyed, the body is never read). The raw-socket matrix writes [refused][valid mutation], [ok GET][refused][mutation], the refusal and then the mutation in a second write after the answer began, and [mutation][refused] (the first came first: it is answered and applies once) for 19 refusals (unknown route, wrong method, query, invalid key, foreign Host, foreign Origin, wrong media type, long URL, GET with a body, unsupported action, missing preset, declared body too large, and, decided after awaits, invalid JSON, unknown field, missing field, static bound, conflicting key, full lease and full run table), for chunked and `Expect: 100-continue` bodies, for a legitimate pipeline that must answer in order (the read behind a mutation sees it), and the same against a server in a SEPARATE process. Every case asserts the answers the client received, that the connection was closed, and that the ledger and both journals, byte for byte, are exactly what the refusal alone leaves. Mutants S15 to S21 remove the mark, the check and the queue (in process and in a separate process) and make a refusal keep the connection alive. Limit: a legitimate pipeline BEHIND a refusal is cut off (the client resends on a new connection). One **equivalent mutant** is listed and shown to survive: the mark through `response.socket` instead of `request.socket`, because under the queue a response always has its socket when its handler runs.

- **C043 F2, the evidence test** (`tests\evidence.cjs`, `tests\evidence.test.cjs`): the recompute no longer skips any folder; it recognises capture manifests by their shape, so the manifests in `evidence\raw` (green, coverage, mutants, browser: 38 pinned inputs each, among them this README, every production file and every test) are recomputed too. `tests\evidence.test.cjs` asserts the exact set of 17 manifests (and an 18th, `evidence-02`, the capture of that very test, which cannot exist while it runs and is recomputed whenever it is present), recomputes every input (size, SHA-256, LF-normalized SHA-256) and every transcript, and shows for EVERY capture, in a scratch copy, that a README byte, a production file byte, a test byte, a stream byte and a changed pin each fail by name. - **C043 F3, the step service contradicts the preset** (`tests\f3-cross-check.test.cjs`, `tests\f3-process.test.cjs`, `tests\f-more.test.cjs`): the first README said an acknowledged step is never trusted without the step service, but only the pending step was asked. Now every acknowledged step of a run that is not being driven in this process is checked against the step service on every inspect, run-again (replay), resume, cancel and unsupported action, in two layers, and the journal health counts `unconfirmedRuns`. (1) The ledger that the step service reports (`leases()`, which is not a step function, so a healthy answer makes no step call: the retained initial tests assert that a re-run, a conflict and an inspect after a restart call nothing) must hold at least the units that the acknowledgement says were reserved after the step; a step journal that lost its tail makes the total fall below. (2) The production composition (`composeService`, which every server and child process uses) also passes `verify`, the step service's own `inspect`: the step must be held as committed with the same effect (lease, units, reserved-after), which catches what a total cannot (a step journal rebuilt with another reservation first, or a gap that other steps filled again). The first step that fails a layer is returned with the step service's own typed code for it (the one `inspect` that is then made). A step that the step service does not hold as committed with the same effect (lease, units, reserved-after) makes the answer the typed `PRESET_STEP_SERVICE_DISAGREES` (503; an inspect is still a 200 read): the unconfirmed step is `unknown` with the step service's own code (`STEP_INTERRUPTED`, `STEP_NOT_FOUND`, `IDEMPOTENCY_KEY_CONFLICT`, ...), the steps after it are listed as not confirmed (the `STEPS_NOT_CONFIRMED` wording, not "never called"), the run state is `stopped` and never `completed`, the effects listed are exactly the confirmed ones (their units equal the ledger), nothing is submitted or journaled, and only `correct-and-resubmit` and `inspect` are offered (a new key replays the confirmed steps, resume of that new run finishes the rest, and the old run is confirmed again). A contradicted run is not resumed or cancelled: the preset journal says it ended and nothing is rewritten. Every envelope carries `stepJournalDiscardedTailBytes` (the bytes the step service discarded at start; `null` for an answer without a run) and the page shows it. Proved with real child processes and file journals for both repros after a hard kill (a flipped final newline: the tail is reported; a cut at a record boundary: only the unconfirmed step shows it), exhaustively for a step journal cut after 0 to 6 records, for an effect the step service holds differently, for an OPEN run whose earlier step was lost (resume and cancel, also for a run that stopped part-way with steps left to do), and in the page (`NOT CONFIRMED`). No false positive: intact journals restart `completed`, and the answer of a run driven in this process is built from the step answers it just received (the call log of a fresh run is still `submit` only, and a counting wrapper shows that the ledger is not read for it while a later inspect does read it). Limit: the step service can only confirm what it records; a refusal (a failed step) leaves no record there and is not cross-checked; a runner opened without `verify` (a test double, not the composition) has the ledger layer only, which a ledger that was refilled by other steps can mislead.

## Browser limit (read this)

The isolated browser helper allows **only GET** and aborts every other method (`testing\browser\isolated.cjs`), so the real browser **cannot POST** a preset. Submitting the form there fails at the network layer and the page reports **UNKNOWN**: no valid response, nothing shown as success, only Retry and Inspect offered. What the real browser observes instead: the declared presets (GET), the read-only inspection of a preset that the test completed from Node and of one still running (progress, effects, controls), and the server-produced transcript, which the server drives over real loopback sockets against private instances (valid run, replay, conflict, every hostile input, a refused step, a duration bound on a manual clock, a cancel while a step is in flight, a restart with an explicit resume) and which the page verifies again. The POST actions themselves are proved by the node:test suites against real sockets and by the page tests against the real service.

The page prints **no server prose**: every answer is validated against the closed envelope (shape, status honesty, listing derived from the steps, wording only from closed catalogs), the HTTP status must be the honest one, and the preset an answer shows must be the one that was sent (unless the key belongs to another preset); the headline, the listings and the controls are derived from the facts by the page. A tampered state, result or failure is rejected and shown as such.

## Resource bounds and the C042 review findings

- **F1** (a guard whose removal passes every test is unproven): the mutants above remove every limit and destroy rule; the refusal flood runs the attacker in a separate process against a server in a small-heap child (`tests\resources.test.cjs`, `tests\attacker.cjs`, `tests\child-server-r3.cjs`) and decides on structure, never on a duration: every attacker socket is closed by the server, every probe GET during the flood is answered, the heap is collected once the connections are gone, and the server read at most 524,288 bytes from one refused connection (a correct server reads one 64 KB chunk: 65,648 bytes at most were measured; without the destroy after the flush it keeps parsing the endless body and read 2,097,152 bytes from one connection, with an event-loop lag of 7 to 24 s in the measured runs, which is why that mutant now dies on the byte count and not on a lag bound).
