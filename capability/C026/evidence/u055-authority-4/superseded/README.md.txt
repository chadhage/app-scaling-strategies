# C026: sequenced WebSocket fixture

A **synthetic, local-only, offline** H005 fixture on `127.0.0.1` (automatic port). It is **not the approved Node.js 24 LTS / Express / App Service Linux control API**: it uses Node built-ins only (`node:http` upgrade plus its own RFC 6455 framing, no `ws` package, nothing installed), validates no production runtime, verifies no identity, stores nothing durable and makes **no Azure call**, no cloud call, no spend and no registration. All business data is synthetic. Node `v22` here is test tooling.

The server **owns every sequence number**. A client may only say `hello`, `resume` with a cursor, or `ack` the next message the server already sent.

## Run it

```powershell
node capability\C026\server.cjs
```

The CLI rechecks current C001 local-probe consent (`approvals.C001`, read-only), binds only `127.0.0.1` on an automatically assigned port, prints one JSON line with the exact origin and process ID, and accepts no host, port, stream size, identity or deployment override. Open the origin in a browser and press **Load server-produced transcript**. Stop it with Ctrl+C. Automation must close its exact returned server handle (`closeServer(server)`).

Routes: `/` (page), `/page.js`, `/styles.css`, `/scope.json` (observed tooling plus explicit non-qualification flags), `/transcript.json` (see the browser limit), `/stream` (WebSocket only; a plain GET is 426 with `Upgrade: websocket`). Foreign Host or Origin headers, queries, writes and bodies fail explicitly, on the plain routes and on the upgrade path alike (an upgrade that carries a body is 400 `UNEXPECTED_BODY`; an upgrade target of another authority is 400 `INVALID_URL`; an empty query `/stream?` is 400 `INVALID_QUERY`). Every refusal says `Connection: close` and the server closes the socket once the answer is flushed, so a client that keeps streaming a body cannot keep the server parsing it. Since U040 a refusal also marks its connection at decision time: nothing the peer pipelined behind it runs, an upgrade included (see the last section).

## Protocol

Frames are JSON text. A fixture stream has `total` 12 messages and a `window` of 3 unacknowledged messages.

| Direction | Frame | Meaning |
| --- | --- | --- |
| client | `{"type":"hello"}` | new session |
| client | `{"type":"resume","session":S,"cursor":C}` | continue session S after cursor C |
| client | `{"type":"ack","seq":n}` | acknowledge the oldest unacknowledged message, and only that |
| server | `welcome` / `resumed` | session, cursor (`c1.<session>.<seq>`), total, window; `resumed` adds `ackedThrough`, `lastSent`, `cursorBehind` |
| server | `message` | `seq` (server numbered), `body`, `redelivered`, `deliveries` |
| server | `acked` | confirmation with the new cursor |
| server | `complete` | everything acknowledged; close 1000 `COMPLETE` |
| server | `error` | typed `code`, then close 1008 with the code as reason |

Rules proved by the tests:

- Strict order, no gaps, no duplicates: sequences count up from 1 and the next message is sent only when the window has room.
- An acknowledgement must be exactly `ackedThrough + 1`. Never sent: `ACK_UNSENT` (and nothing is recorded). Repeated: `ACK_DUPLICATE`. Skipping: `ACK_OUT_OF_ORDER`. Not a positive integer: `ACK_MALFORMED`.
- A client cannot name a message sequence: a `message` frame or a `seq` outside `ack` is `CLIENT_SEQUENCE_FORBIDDEN`. Other typed failures: `MALFORMED_JSON`, `MALFORMED_MESSAGE`, `UNSUPPORTED_MESSAGE`, `UNEXPECTED_FIELD`, `HELLO_REQUIRED`, `ALREADY_ESTABLISHED`, `SESSION_LIMIT`.
- Resume checks the session (`SESSION_UNKNOWN`), the cursor format (`CURSOR_MALFORMED`), the owner (`CURSOR_FOREIGN_SESSION`), the future (`CURSOR_FROM_FUTURE`) and a claim beyond the recorded acknowledgement (`CURSOR_AHEAD_OF_ACK`). A cursor **behind** the server record continues after the **server** record (`cursorBehind: true`); an acknowledged message is never sent again.
- After an abrupt close (socket destroyed, no close frame) a resume redelivers every unacknowledged message **once per resume**, flagged `redelivered: true` with a rising `deliveries` count, before any new message. A resumed completed stream answers `resumed`, `complete`, close 1000 and sends no message.
- A second connection that resumes a session takes it over; the first receives `SESSION_TAKEN_OVER` and is closed.
- Framing: client frames must be masked, reserved bits zero, control frames final and at most 125 bytes (also in the 64-bit length form: 1002), lengths minimal, text valid UTF-8, messages at most 4096 bytes in at most 64 frames (every frame counts, empty continuation frames too: 1009 `TOO_MANY_FRAGMENTS`). Violations close with 1002, 1007, 1003 (binary) or 1009; pings are answered with pongs; a client close is echoed. A violation closes the connection and discards messages parsed from the same TCP chunk before it: nothing unvalidated is ever recorded and a resume redelivers.

## Browser limit (read this)

The isolated browser helper blocks WebSockets, writes and foreign origins (`testing\browser\isolated.cjs`, see C020). The browser therefore **does not open a WebSocket here**. `GET /transcript.json` makes the server run a real WebSocket conversation against a private fixture instance (hello, acknowledgements, an abrupt disconnect, a resume with redelivery, completion, and forged probes) over real loopback sockets, and returns the recorded transcript with session ids aliased. The page fetches that transcript, **verifies it itself** (order, no gaps or duplicates, redelivery only of unacknowledged messages, acknowledgements only of sent messages, completion only after every acknowledgement, plus the required evidence and typed failures) and shows `VERIFIED` or `REJECTED`. A missing or unavailable transcript, and any alteration of what the page checks, is REJECTED and clears the display. The page checks: event numbering, first deliveries exactly 1, 2, 3, ... per session, redeliveries only of unacknowledged messages and never twice on one connection, acknowledgements only of sent messages in order with a matching cursor, resume and completion positions, no session welcomed twice, and the presence of an abrupt disconnect, a resume, a redelivery, a completion and the five required typed failures. It does **not** check message bodies, delivery counts above two, the frames the client sent, close codes, the `total`, `window` and `kind` labels, or whether a transcript came from a real conversation: a hand-written transcript with the right shape is shown as `VERIFIED`. The page is a display aid for a server-produced transcript, not a proof; the proof is the node:test suites over real sockets. After every load, recovery and retry the browser test scans the rendered table for repeated event ids and reconciles the message rows with the verified counts (`DOM_EVENT_IDS` lines in the archived browser run). The real-browser observation is of the transcript page, **not a browser WebSocket**; the WebSocket behavior itself is proved by the node:test suites against real sockets.

## Operating envelope

C001's design remains Node.js 24 LTS / Express / App Service Linux; this fixture's evidence records the test runtime separately. Every resource a client can make the fixture hold is bounded, and the numbers are in `limits` (exported by `server.cjs`): messages of at most 4096 bytes in at most 64 frames, at most 64 KiB of output a client has not read (past it the connection is dropped, its session stays resumable and the server emits a `limit` event `{ code: 'OUTBOUND_BACKLOG', limit }`; a close frame could not reach a client that does not read), at most 128 TCP connections (more are dropped at accept), a window of 3 and 32 sessions. Sessions are never released: after 32 `hello` frames in total a fixture instance answers `SESSION_LIMIT` until the process restarts (a restart also forgets every session: a resume then fails `SESSION_UNKNOWN`). There is no idle timeout on WebSocket connections: an idle connection stays until its peer closes it, `closeServer(server)` destroys it (it destroys every accepted socket, refused upgrades included) or the connection cap applies. The 426 answers carry `Upgrade: websocket` but not the `upgrade` connection option, because every refusal says `Connection: close`. No identity verification, server-enforced role or lease boundary, durable store, slot or container qualification, deployment, registration or spending exists here. Native OS, SKU, region, tenant, subscription and resource group remain unapproved. IaC is N/A. `imports.json` pins the two accepted C001 files used (`contract-guard.js` for the consent recheck, `approved-contract.js` in tests) by commit, tag and SHA-256.

## U040: nothing pipelined behind a refusal (defect fix after audit U038; amends the accepted card)

The audit found that a valid `Upgrade` `GET /stream` plus a masked `{"type":"hello"}` frame pipelined in ONE TCP write behind any refused plain request created a hub session (`hub.sessionCount()` +1; 10 of the audit's 15 refusal variants, and the client saw `[404,101]` or `[200,101]`, so it could not read the refusal as an answer): Node emits `upgrade` for such a request although the refusal was just decided. No HTTP route changes anything, so the effect was a hub session. Now `server.cjs` marks the connection at decision time, synchronously: `closing`, a `WeakSet` filled inside `fail` with `request.socket` (never `response.socket`, which is null for an answer queued behind another one). The request handler and the `upgrade` listener drop everything on a marked connection without effect and, up to the drop budget of fix 2 (16 requests, see the last section), WITHOUT destroying the socket: destroying at once cut off a refusal queued behind an earlier answer (`[G][R][M]` gave the client only the 200); the refusal says `Connection: close`, so Node ends the connection once it is flushed, and the client receives the earlier answers and the refusal, then a closed connection. Node's own answers go through the same path: `checkExpectation` (typed 417 `EXPECTATION_FAILED`), `checkContinue` (the handler decides: a refused request gets no `100 Continue`, a read without content is answered without one, which RFC 9110 allows), `requireHostHeader: false` (a request without Host is the typed 421 `LOCAL_HOST_REQUIRED`) and `clientError` (typed 400 `MALFORMED_REQUEST`, 408 `REQUEST_TIMEOUT`, 431 `HEADERS_TOO_LARGE`, ended after the flush; a socket that already carried an answer gets none). The one route that answers after an await, `/transcript.json`, marks its connection at dispatch and answers `Connection: close` on success and on failure: a request pipelined behind it cannot be ordered against it, so it is dropped, and a legitimate pipeline behind a transcript request loses its later answers (a valid GET followed by a valid upgrade is still served).

Proved by `tests\u040-pipelining.test.cjs` and `tests\u040-node-own.test.cjs` over 13 refusals (404, 405, 421, 403, 426, three 400 kinds, an invalid URL, a failing transcript, an unknown `Expect`, `Expect: 100-continue` and no `Host`) in six forms each, in both framings, in this process and in a separate node process, plus two live instances in one process (a refusal on one never touches the other; closed first-in-first-out, last-in-first-out and twice); 20 hand-chosen mutants of the added guard lines were all killed by named tests (a 21st is in `tests\u040-mutants.cjs`, not archived). The exact commands, the evidence under `evidence\u040`, the addendum mechanism and its limits are in `U040.md`. `server.cjs`, `README.md`, `tests\evidence-final.test.cjs` and `tests\coverage-gate.cjs` are superseded by `evidence-index-addendum-1.json`, which names the replaced bytes of each; `evidence.json` and every archive of the first and fix publications are unchanged.

What was and was not probed. Probed (raw sockets, the fixture in this process and in a separate node process): the refused request framed HTTP/1.1 and HTTP/1.0 with `Connection: keep-alive`, the upgrade framed HTTP/1.1 and HTTP/1.0, the pipelines `[R][M]`, `[G][R][M]`, `[R][T]` and `[G][R][T]` in one write (M a valid upgrade with a masked hello frame, G a valid read, T a read of `/transcript.json`), two writes (the second after the answer, and 5 ms later), `Content-Length` and chunked bodies, unknown and `100-continue` `Expect`, no `Host`, unparsable bytes, an h2c upgrade attempt (refused, never accepted), a refusal decided after an await (a failing transcript), a successful transcript, and 50 reads behind one refusal. Not probed: HTTP/2 (the HTTP/2 prior-knowledge preface; the listener is HTTP/1 `node:http`), TLS, proxies, `Keep-Alive` header parameters and any keep-alive negotiation beyond `Connection: keep-alive`, a real header flood and a real request timeout (the 431 and 408 answers are only exercised by emitting the parse error on the server with a stub socket, not by 16 KB of headers or a 5 s stall), and `[M][R]` (an upgrade followed by plain HTTP bytes: those bytes are WebSocket frames, a framing error, not a pipelined request). Unchanged and noticed: Node and this fixture accept a WebSocket upgrade in an HTTP/1.0 request (RFC 9110 says a server ignores `Upgrade` there); it is not behind a refusal and was left alone. Two timing facts: the 5 ms two-write variant of the audit is a race (the archived RED runs show 11 of 15 variants creating a session in this process and 10 of 15 in the separate process for `red-01`, and 10 and 10 for `red-02`: the one extra case is the 5 ms write arriving before the server closed the connection, which the fix also drops), and a client that writes after the server closed can make the OS reset the connection before it read the refusal, so that one form requires only that the answers received are a prefix of the expected ones.

Legitimate requests BEFORE a Node-own refusal (rev-C059 N1, the third pipelining hole, found in servers that queue requests per connection; this fixture has no queue of its own, only Node's response order, and the probe confirmed that it is not affected). `tests\u040-node-own.test.cjs` sends one to three valid reads before each refusal that Node decides while it parses a request head (an unknown `Expect` on a GET and on a POST with a body, no `Host` in both framings, `Expect: 100-continue` on a refused path, and bytes Node cannot parse) in the shapes `[X]`, `[G][X]`, `[G][G][X]`, `[G][G][G][X]`, `[G][G][X][G]`, `[G][G][X][M]`, `[X][G][G]` and `[P][G][X]` (X the refusal, P a refused POST with a body): 56 rows per mode, in this process and in a separate node process. The earlier reads are answered in order, then the typed refusal with `Connection: close`, then the connection is closed; nothing behind the refusal is answered or run and no session is created. A burst of 128 sockets (the connection cap) that each send `[G][G][X]` in one write ends with every socket closed by the server (counted, no clock) and a legitimate read is answered afterwards. One limit, tested as such: a parse error has no request to queue an answer behind, so behind earlier pipelined requests the typed 400 is not promised: the connection is destroyed, as a plain `node:http` server does when an answer is in flight (a control test runs one without any `clientError` listener: after one to three pipelined reads and a parse error it answers at most the first read and closes), so the first earlier answer may arrive and later ones are lost. It never upgrades, never answers more than was expected and always closes. Deferring the 400 until the in-flight answers have been flushed would remove the limit; it is an open item.

### U040 fix 2 (addendum 2): what a marked connection may still make the server read, and the Expect mark

The independent review of U040 rejected it on one major, F1, a regression of fix 1 itself: the requests that fix 1 DROPPED were never answered and never stopped the socket. Node pauses a pipelining connection only when the output queued behind an unfinished answer reaches the write high-water mark, and a dropped request writes nothing, so after a refusal (or while `/transcript.json` was in flight) Node kept parsing and holding one request object and one response object per pipelined request: a child started with `--max-old-space-size=48` died at 3 sockets (exit 134, `Reached heap limit`) in 9 of 9 reviewer runs, where the pre-U040 bytes survived 7 of 7. The first RED of fix 2 (`evidence\u040-2\red\f2-red-01-new-tests-committed-bytes`, archived before the fix) reproduces it in three variants: each of 3 sockets sends a real `GET /transcript.json`, a refused `GET /nope` or a held (never settling) transcript read, and then 50 blocks of 64 KB of pipelined `GET /scope.json`, reading nothing. That Host-bearing request has roughly 1,300 copies per block, depending on the automatic-port width; it is not the smallest parsed request. The final RED and control have four variants (real, refuse, hold, expect); expect's survival test passed on the fix-1 bytes, while its drop-budget assertion failed.

The fix is a drop budget in `server.cjs`. A marked connection has a count of the requests dropped behind the mark (a `WeakMap` next to `closing`). The first 16 (`MAX_DROPPED_REQUESTS`) are dropped quietly, so the earlier answers and the refusal of `[G][R][M]` are still delivered and the refusal's own `Connection: close` ends the connection; the 17th destroys the connection, and the server emits a `limit` event `{ code: 'DROPPED_REQUEST_BACKLOG', limit: 16 }` once (like `OUTBOUND_BACKLOG`; it is not a key of the frozen `limits` object, which `hardening.test.cjs` pins). The corrected code comment distinguishes the 18-byte `GET / HTTP/1.1\r\n\r\n` without Host from the review's actual flood. The review observed 3,639 request events per 64 KiB read in its flood shape. An aligned read containing only 18-byte requests fits 3,640 complete requests; after one 18-byte marking request, 3,639 further requests fit. Thus `floor(65536 / 18)` is 3,640, not 3,639; the historical observed count is not a universal parser maximum. `requireHostHeader: false` lets Node parse and dispatch that shape; the fixture itself refuses the missing Host with typed 421, not a successful page response. Destroying on the 17th drop ends later reads, but does not undo the objects already created from the current read; they are released when the socket closes. An upgrade behind a mark is dropped without being counted: Node stops parsing after an `upgrade` event, so no later request can follow it. The reviewer tried a bare `socket.pause()` at the two mark sites and the child still died; the budget is the design of C009 (a lane depth of 16 that destroys the socket at the first request beyond it).

Minor m1 (a sibling of the root cause, found by the same review): one write of `GET /scope.json` with `Expect: 100-continue` followed by a valid `GET /stream` upgrade and a masked hello created a hub session AFTER an answer that says `Connection: close`. `checkContinue` goes through the one request path, which answers without `100 Continue`; Node then forces `Connection: close` on that answer, but the connection was not marked, so the pipelined upgrade (already parsed from the same read) ran. Now the one `send` path marks the connection whenever `response.shouldKeepAlive` is false after `writeHead`, that is whenever Node forced the close; the upgrade, and any read, pipelined behind such an answer is dropped and counted. The same bytes without `Expect` still give `[200, 101]` and one session.

Limits, stated as measured and as not probed:

- Beyond the budget the connection is destroyed at once: a peer that pipelines more than 16 requests behind a refusal or a pending `/transcript.json` in one read may lose the refusal, the transcript answer itself, and earlier answers (the operating system may reset a connection that still has unread data, and Windows then drops what the client had not read). The within-budget earlier-answer promise does not make an unresolved transcript finish; `[G][R][M]` and every shape of fix 1 are within the budget.
- Node parses a whole read before a destroy stops subsequent reads, so each flooding socket still costs the request and response objects of that read. The accepted U040 review measured about 6 MB per socket for this shape, about 0.8 GB extrapolated at the 128-connection cap, and a 12 to 15 s event-loop stall with 32 such sockets. These are historical observations and an extrapolation, not a memory or latency guarantee. The minimum-shape observations were 1 socket: peak 16 MB and 3,639 requests; 3 sockets: peak 21 MB; 8 sockets: peak 54 MB; 32 sockets: 32 limit events and 116,448 requests, followed by a legitimate GET 200. The Host-bearing shape at a 48 MB heap survived 12 sockets (peak 42 MB) and 16 sockets (review sampling: 38 to 48 MB), and died with exit 134 at 24. The earlier 50 ms sampler's 19 MB observation at 16 sockets missed the reviewer's higher peak; its old evidence is retained, not relabeled. The tests use structural counters and the three-socket F24 shape, not an absolute memory, CPU-time or wall-clock pass criterion. The 128-connection cap bounds socket count, not a useful global heap or latency guarantee.
- m2 (pre-existing, identical on the parent commit; documented, not fixed): the upgrade listener answers with a raw `socket.write` while Node still holds the answers of earlier pipelined reads, so `[G][G]` followed by an upgrade that the listener refuses gives `[200, refusal]` (the second read's answer is lost; `[G][G][G]` followed by a valid upgrade gives `[200, 101]`). The 20 x 4 loop of fix 2 found that this is wider than first stated (`f2-loop-01-20x4`, retained as a failed attempt): in 1 of 20 runs, in the separate process, the client got only `[200]`, so the refusal itself was cut off (the connection is destroyed before the refusal is flushed; probably Node's queued answer written to the socket that the raw refusal had already ended, not isolated). The client never gets a second read answer, never a hub session, and no state changes. Closing it means deferring the raw refusal and the 101 until the earlier answers have been flushed, which is not trivial and was not attempted. `u040-budget.test.cjs` pins the invariant that holds (`[200, refusal]` or `[200]`).
- m3 (documented by fix 1, kept true): a parse error behind earlier pipelined reads gets no typed 400 and the answers after the first earlier one are lost, and the first one too when the destroy cuts it off; a plain `node:http` server does the same (the control of `u040-node-own.test.cjs`). `u040-budget.test.cjs` pins `[G][bad request line]` as at most `[200]` and closed.
- m4 (kept true, boundary clarified by U055): a plain read behind a SUCCESSFUL `/transcript.json` answer is dropped (`[T][G]` gives one answer), and the drop is counted. In one write, [T]+16 GETs gives [200] and no limit event; [T]+17 GETs gives [] and exactly one DROPPED_REQUEST_BACKLOG event: the transcript answer itself is lost. A held transcript follows the same 16/17 boundary; at 16 the connection remains open until the producer resolves or the peer closes it. At 17 it is destroyed even if the producer never resolves. `tests\u055-boundary.test.cjs` checks the real producer and a manually released held producer in a separate server process without a wall-clock assertion.
- Not probed (unchanged from fix 1): HTTP/2 and h2c prior knowledge beyond the refusal rows, TLS, proxies, `Keep-Alive` parameters, a real 16 KB header flood and a real 5 s request timeout (the 431 and 408 answers are exercised with a stub socket). The seeded fuzz covers eight refusal kinds, the transcript and Expect marks, valid reads, assets, POSTs, bodies and chunked bodies behind the mark, a 3 KB header and upgrades; it does not cover HTTP/1.0 inside the fuzz (the budget rows cover HTTP/1.0 keep-alive), request bodies larger than a few bytes behind a mark (not probed), or two-write splits as an exact oracle (a split may reach a connection that the refusal already closed).
