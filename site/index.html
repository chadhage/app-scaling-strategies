Repository explainer for chadhage/app-scaling-strategies

App Scaling Strategies

A specification for moving an n-tier web application between versions and capacity levels on Azure without interrupting its users, together with a plan, and local rehearsal tooling, for demonstrating it. This page answers seven questions about the repository using three of its documents: the README, the backlog and the kanban.

1Why this repo exists

Short answer. Swap, revision and rolling-update features decide where traffic goes. By themselves they do not guarantee that an in-flight request, a session, an upload or a transaction survives the change. The repository exists to state what has to be true for that to hold, to define how to measure it, and to plan a way to demonstrate it that does not depend on dashboards or configuration screens.

The stated problem, scope and goal Specified

Problem
Scaling a web application under high-availability conditions is hard because the disruption users can tolerate during a swap approaches zero.
Scope
Show the strategies for scaling an n-tier web application with no interruption to the end user's experience.
Goal
Move users across application slots with 99.999% success at achieving zero interruptions.
Reading of the goal
The percentage counts transitions, not endpoint uptime. An endpoint can stay up while a user's journey across a swap breaks, and the README treats that as a failure.

Where assumptions about "zero-downtime" features break Specified

The second and third columns restate the README's key findings, which summarize the Microsoft Learn pages listed under Sources. The first column is this page's framing of the assumption each finding contradicts. This page has not re-checked the findings against current documentation, and the README itself says to verify OS, SKU, regional availability and platform limits before implementing each case.

Common assumption, recorded behavior, and what a demonstration has to do about it
Common assumptionWhat the README recordsConsequence
A new slot adds capacity. App Service deployment slots run on the plan's existing instances. Reserve headroom for the overlap, or use separate plans.
A passing health probe means the candidate is ready. A probe says little about dependencies, effective configuration, authentication, state compatibility or latency. App Service swap warm-up accepts any HTTP response unless acceptable statuses are configured (WEBSITE_SWAP_WARMUP_PING_PATH and WEBSITE_SWAP_WARMUP_PING_STATUSES). Gate readiness on dependency checks and representative journeys, not on one response.
Keeping the old slot makes the swap safe. A native swap recycles the former production workers, and keeping the old slot does not prevent that. Long-running work can be abandoned. Use draining, durable continuation or independently controlled deployments.
A 10% traffic setting means 10% of users moved. Slot-routing cookies pin clients to a destination. Observe where users actually went and what is left on the old side.
Autoscale behaves the same with slots. App Service automatic scaling and rule-based autoscale are different mechanisms. HTTP-based automatic scaling does not currently support deployment-slot traffic. Pick the mechanism the workload supports.
A Functions slot swap is zero-downtime. It is not guaranteed. Executing functions can be terminated. Test execution recovery and consider other update strategies.
Five-nines uptime implies five-nines transitions. They measure different things. Score user journeys that cross a transition, not endpoint availability.

Three further cautions from the same document:

  • A 0% traffic allocation is not an access boundary for a live staging endpoint. Protect candidate environments, and keep warm-up or shadow traffic from causing real duplicate side effects.
  • Rollback limits blast radius. It does not erase interruptions users already experienced.
  • Routing through an external layer gives more control over the lifecycle, but it does not remove the chance of platform restarts.

Why a demonstration harness Planned

Whether a given journey survives a transition depends on SKU, region, load, state and the mix of versions in flight. A written strategy cannot settle that. The backlog therefore plans a browser-accessible harness: pick a scenario, run it, observe what actually happened to the simulated users, then export or reset the run, without installing the Azure CLI, kubectl or application-development tools.

The premise, stated in the backlog's definition of done, is that configuration state and probe results are not evidence. A passing health probe or a 100% traffic weight does not show that users migrated. Client-observed journeys do.

3What it is

Short answer. A specification, a plan and some local tooling. The README specifies 150 scenarios and the rules for judging them. The backlog turns them into 171 work items for a web demonstration harness. The kanban slices those into 414 small cards. The work accepted so far is local: synthetic browser lessons and local capabilities. It is not a library, a set of deployment templates or a set of measured results.

4How it supports its claims

Short answer. It does not deliver zero interruption by itself. It makes the claim checkable: a transition strategy with explicit gates, a definition of failure and of the denominator, a statistical bound, a harness design that reports what happened rather than what was configured, and delivery rules that block false completion. Today the strategy, metric, statistics and delivery rules are written down. The harness design is planned and partly built as local, synthetic tooling. None of it is native Azure evidence yet.

A transition strategy with explicit gates Specified

The README states its central strategy in one line: overlap before handoff, compatibility during coexistence, and verified retirement afterward. Old and new capacity exist side by side with admission controlled; both versions work against the same state and contracts while they coexist; and the old side is removed only when nothing depends on it. Slots are one mechanism for this, not a solution to zero-interruption n-tier scaling on their own.

Other transitions the README allows:

  • CREATED, WARMING or READY may become ABORTED before any user is exposed, with failure evidence and safe cleanup.
  • An exposed candidate that turns unhealthy may become QUARANTINED: stop further exposure, run the tested recovery path, and keep the interruption records.
  • DRAINING or RETAINED may return to ACTIVE as a rollback, but only after fresh readiness, capacity and compatibility checks.
  • After an irreversible data change, forward recovery may be the only option.

Gate decisions rest on recorded evidence: deployment identity and epoch, endpoint, desired versus effective routing, readiness freshness, available capacity, compatibility versions, remaining work, ownership and checkpoints, the rollback deadline, and explicit errors. Promotion and retirement must not rely on a stale controller command or on a single successful response. If the platform gives no reliable progress signal, the uncertainty is recorded and no completed state is invented. The lifecycle does not override platform behavior such as native swap recycling or autoscale termination.

What counts as an interruption Specified

The unit of measurement is one declared user journey that crosses a deployment or capacity transition. A journey is interrupted if any of these happens:

  • a user-visible error, a timeout, or a broken connection the journey needs;
  • completion later than the journey's agreed latency budget;
  • an unexpected logout, lost session or form state, or broken navigation or assets;
  • a missing or duplicated business effect;
  • data freshness, ordering or consistency outside the declared contract.

A retry or reconnect counts as "seamless" only if correctness, state and user experience stay intact within the original journey budget. Unlimited retries and success-shaped fallbacks must not hide failures.

Outcome classes and how each is counted
OutcomeTreatment
Uninterrupted successful transitionThe intended migration is evidenced and the whole journey meets every acceptance criterion. Counts as a success.
Safe abort before exposureProduction stays usable, but no user migrated. Reported separately; not a migration success.
Interrupted transitionCounts as a failure, including failures that happened before a rollback.
Unverified or unsupportedMissing evidence or a platform limit. Not counted as a success.

Two rules follow. Users who stayed on the old deployment prove nothing about migration just because their requests succeeded. And a failed or uncertain transition that had started cannot be dropped from the denominator.

The metric, and how much evidence it takes Specified

success = uninterrupted successful transition journeys
          / all attempted transition journeys

target:  success >= 0.99999        (interruption probability <= 0.00001)

The event boundary, affected population, observation window and outcome attribution are fixed before a run. Results are reported per hosting model, cohort, protocol, load and failure condition as well as in aggregate. An empty sample is no evidence, not 100%. Endpoint uptime, throughput, average latency and tail percentiles stay useful as diagnostics but do not replace the journey metric.

The sample size comes from a one-sided bound. With zero failures in n independent, comparable trials:

p_upper = 1 - 0.05^(1/n)
n >= ceil( ln(0.05) / ln(1 - 0.00001) ) = 299572

So roughly 300,000 independent zero-failure transitions are needed for a 95% bound at 0.00001. The README presents this as an illustration, not a universal sample size: users in one swap can share a correlated failure, and repeated requests from one user are not independent transitions. What has to be counted is independent rollout events across varied failure contexts.

Zero-failure confidence bound

Assumes independent, comparable trials and no observed failures. If failures occur, more trials are needed for the same bound; this calculator does not model that.

Editorial Practical reading: a handful of rollouts cannot support a 99.999% claim, however many requests they carried. The claim needs on the order of 300,000 independent transitions without an interruption, and more if interruptions occur.

Inside the harness, live native operations, fault emulation, recorded replay and simulation are labeled separately. A simulation cannot certify a native strategy. Zone and region isolation experiments are outage proxies unless the real failure was observed. Each result shows three things independently: the verification verdict, the user-transition outcome and the cleanup status. The supported outcomes are uninterrupted transition, safe abort before exposure, interrupted transition, expected interruption observed, unsupported, unverified and cancelled.

Controls on the harness Planned

  • Authenticated roles, server-side authorization, and per-conductor leases with an ownership check on every resource target.
  • Bounded inputs, concurrency, runtime, capacity and spend. Concurrent over-admission is rejected.
  • Management secrets stay on the server. Browsers never receive Azure management credentials or any ability to run arbitrary ARM or kubectl commands.
  • Synthetic data only. Faults are injected only into leased resources, never into production, another conductor's resources or the harness's own management plane.
  • Runs are durable and commands idempotent. A browser refresh does not cancel a run, duplicate commands have one effect, and cancellation reconciles with in-flight platform actions instead of pretending to undo them.
  • Reset and lease expiry clean up idempotently. A failed cleanup stays visible and alerts an operator.
  • Every run saves a versioned manifest and a sanitized evidence export. A rerun starts from a known fixture state and keeps earlier results.

Controls on delivery Planned

  • Each scenario has two required kanban children: an A card (portable rehearsal) and a B card (native proof). Finishing A gives a learning asset. It does not give a native demo or evidence of uninterrupted migration.
  • Every card has one owner or pair, one reviewable change set and one observable acceptance result. A cards target 1–2 focused hours; C, B and X cards target 2–4.
  • The working order is: BDD specification, a genuine failing test, the IaC step (or an explicit N/A for a lesson with no resources), implementation, green tests and real-browser checks, scoped tagged publication, then acceptance by someone other than the author. A worker cannot award its own Done credit.
  • The board has three columns. To Do holds at most 2N cards and In Progress at most N, with one active card per contributor, where N is the number of active contributors. Review, tests and acceptance stay inside In Progress.
  • Completion credit follows Kano classes: D (must-be), S (satisfier) and L (delighter). With d, s and l as the counts of accepted cards in each class, the totals must satisfy the two inequalities below.
s + l >= 4 * d
s     >= 6 * l

In plain terms, must-be work is admitted only after enough value work is done, and each optional delighter needs six designated satisfiers first. The kanban adds that safety is never waived to satisfy a quota: live features stay disabled until their must-be guards pass. Planning inventory earns no credit. The ledger records admitted work, owners, acceptance, commits and tags, hints and shared lessons, and the actual totals.

5How to use it

Short answer. Three ways, in order of what is available today. Open the local learner harness and work through synthetic lessons: no server and no Azure account. Use the README as a test plan for your own system. Or, if you are building the harness, pull cards from the kanban. A hosted harness that runs real Azure experiments is planned and is not available.

Try the local lessons Specified

These steps follow the README's "Try the local demonstrations" section.

  1. Clone the repository: git clone https://github.com/chadhage/app-scaling-strategies.git
  2. In the clone, open capability/local-harness/index.html directly in a browser. No server or Azure account is needed. The folder is on GitHub, but GitHub shows its source there and does not run it.
  3. Search and filter the 150 scenarios and two guided workflows. Open a scenario's preparation and limits view.
  4. Open an accepted portable lesson. Use its synthetic controls, run its failure cases, and reset it.
  5. Treat availability labels as a snapshot. The catalog names the acceptance snapshot it reflects and is not a live feed. For newer accepted work, evidence and the unblock work that gates native proof, use the kanban's links and its ledger.

Two pieces need more than opening a file

The versioned getProfile fixture (C020) and the isolated lesson host (C041) are HTTP-backed. They have their own bounded, loopback-only launch and cleanup instructions. Their HTML cannot be run by opening it as a file, and their listeners should not be exposed publicly.

Local lessons use synthetic data. A lesson teaches a failure mode and the check for it. It is not native evidence and does not complete a scenario's source demonstration.

Use the README as a test plan for your own system Editorial

No tooling from the repository is needed to do this. The README is written so that it can be applied directly.

  1. Declare the operating envelope before each demonstration (worksheet below). A combination that is unsupported, or an outage outside the envelope, is reported as a limitation and never counted as a success.
  2. Choose scenarios. Start with the README's recommended sequence (table below), then widen with the coverage matrix.
  3. Write each chosen scenario as given/when/then in your environment, and apply the shared acceptance criteria to it.
  4. Instrument. Stamp a version in every tier, add a client-side oracle that checks content and effects as well as status codes, and record observed routing, capacity and readiness.
  5. Run and record using the demonstration record fields below.
  6. Score with the outcome classes and the metric. Keep failed and unknown transitions in the denominator.

Operating-envelope worksheet

  • Hosting model, deployment format, SKU, region and the platform limits that apply.
  • User journeys, protocols and compatibility requirements.
  • Minimum, normal and peak load, including the demand the overlapping deployment adds.
  • Journey latency budgets and the maximum supported request and job durations.
  • Dependency capacity, data freshness, ordering and transaction guarantees.
  • Supported failure conditions and the capacity that must survive them.
  • Drain, rollback-retention and recovery budgets.

Demonstration record

  • Scenario ID, platform and format, deployment epochs, and the operating envelope.
  • Preconditions, trigger, routing changes and the intended affected population.
  • Client-observed journey outcomes, plus tier and version evidence end to end.
  • Capacity, readiness, active-work, data-correctness and latency observations.
  • Injected failures, recovery actions, safe aborts, interruptions and unknown outcomes.
  • Effective routing and ownership of work and state after rollback or retirement.
  • The evidence behind the conclusion, and the limits left unresolved.

Worked example: S001, warm blue-green handoff

Condensed from the README's first foundational scenario.

Given
A live production deployment, a candidate that can be routed independently, and enough compute and dependency capacity for the two to overlap.
When
The candidate is provisioned and registered as WARMING; its instances, dependencies, configuration and journeys pass the readiness gates; it becomes READY; and eligible new admissions are routed to it.
Then
Migrated journeys keep authentication, state, correctness and latency budgets. Work already admitted finishes, or continues through a tested durable handoff. Actual routing and drain progress are verified. The old deployment stays available for remaining clients and for rollback, and is retired only after the routing, drain, ownership and retention gates pass.

If you are implementing the harness Planned

  1. Read the backlog's Experience and access model, Shared definition of done, and Priorities and dependencies. Then read the kanban's Atomic card contract, Entry gates and Kano policy.
  2. Check the ledger before taking a card. Only ready, unowned work is pullable, and a returned remainder stays in To Do, marked not ready, until its gates pass.
  3. Choose by gate. An A card needs only the source documents and the portable lesson contract, so it can start without Azure. A B card needs the core capabilities, the data fixtures and a qualified host, among other gates.
  4. Follow the lesson contract for an A card: a standalone, browser-openable bundle with a small interactive exercise. It declares its source ID, objective, preconditions, actions, synthetic input or trace, expected assertions and limits. It says "Training rehearsal - synthetic data - not a live Azure result", makes no management calls, holds no credentials, and works from the keyboard.

The planned conductor journey Planned

This is how the hosted harness is meant to be used once it exists. It does not exist yet.

  1. Select a scenario card and read its purpose, expected outcome, limits and prerequisites.
  2. Choose a supported host, deployment format, load profile, user cohorts and operating budgets.
  3. Review the estimated cost, duration, permissions and leased resources, then approve the run.
  4. Open the sample application and start real or synthetic user journeys.
  5. Run guided actions: warm, promote, scale, inject an approved fault, drain, roll back.
  6. Watch actual routing, deployment versions, state transitions, client outcomes and dependency behavior.
  7. Review the evidence-backed result, export a sanitized report, and reset or release the sandbox.

Both a guided single-step mode and an automated complete-run mode are planned. A browser refresh or disconnection must not cancel a durable run.

6Where to use it

Short answer. Today it runs locally, in a browser, on synthetic data. It applies to n-tier web applications on Azure App Service, Container Apps, AKS and Functions, with Spring Boot as a runtime variant. Real Azure runs are planned for leased sandbox resources, never for production, and none is approved yet.

Application shape Specified

  • Tiers. Frontend, API, database, cache, messaging and workers, exercised together. Verifying each tier alone is not enough, because scaling one tier can overload another.
  • Protocols. Short and long HTTP requests, multipart upload, large download, WebSocket, server-sent events and gRPC streaming.
  • State. Sessions, authentication keys, uploads, workflow state, caches and tenant ownership.

Where it does not apply Editorial

  • Clouds other than Azure, and Azure services outside the hosts listed above.
  • Workloads that are not n-tier web applications.
  • Spring Boot as a deployment platform: it is a runtime that sits on one of the hosts.

7When to use it

Short answer. Use it when a release or scale event must not interrupt users and you need evidence rather than assurance. Before running any scenario you should be able to state your latency budget, your state model and your version-compatibility plan. The catalog will mostly show you which of those are missing. The local lessons have almost no prerequisites. Native Azure runs have several that are not yet met.

Prerequisites for running scenarios on your own system Editorial

Derived from the README's scenarios and declaration rules. Each item is something a scenario would otherwise expose as a gap.

Platform and capacity

  • Host, format, SKU, region and limits are written down, and the limits are checked against current platform documentation.
  • There is headroom for the overlap at peak load, in one plan or by using separate plans.
  • Dependencies can absorb the extra instances: database connections, caches and outbound connections.

Application and state

  • Sessions, authentication keys, uploads and workflow state are shared or durable, or you know exactly what is instance-local.
  • Requests that outlast a drain period have a durable continuation.
  • A retried POST or a redelivered message cannot repeat a business effect.

Compatibility

  • Old and new versions can coexist: frontend and API contracts, schema changes (expand, migrate, contract), cache payloads, event schemas, static assets, workflows and configuration.
  • A rollback path exists, or you have decided that forward recovery is the plan.

Observability and evidence

  • Every tier reports its version, so you can see where each user actually went.
  • Readiness checks cover dependencies and representative journeys, not one status code.
  • A client-side check looks at content and effects, not only HTTP status.

Test hygiene

  • Test data is synthetic, and anything with external side effects runs against a sandbox.
  • Candidate environments are protected. A 0% traffic allocation is not access control.
  • Each journey has a declared latency budget and a maximum request or job duration.

Statistical honesty

  • If you intend to claim 99.999%, you have a plan to collect on the order of 300,000 independent transitions and to analyze correlated outcomes.

Prerequisites for the local lessons Specified

  • A browser that opens local HTML files. No server, Azure account or credentials are needed for the learner harness.
  • The getProfile fixture and the isolated lesson host are the exception. Follow their own instructions, keep them on loopback, and do not expose them publicly.
  • To run the repository's automated tests, the README names Node.js 22.23.4 as the validated test-tooling runtime.

Prerequisites for native Azure runs Planned

  • Approvals. The README lists IaC generation, identity registration, live Azure execution, deployment and expenditure as unapproved. The kanban adds that the exact target, SKU and region, and separate scaffold and deployment approvals, are still required.
  • The harness foundation. Every scenario demo (D-S) requires BASE, which is H011 (the deployed harness), P005 (leased data, cache, storage and messaging fixtures) and one qualified host adapter: P001, P002, P003 or P004.
  • Kanban gates. A B card needs the core capabilities, the data fixtures and a qualified host, among others listed in its row.
  • A qualified configuration. Proof does not transfer between hosts or formats.
  • A leased sandbox, a cost estimate and a budget. Experiments classed P2 also need explicit cost and risk approvals.
  • Recorded decisions (H001). The supported configuration matrix, budgets, capacity, duration limits, data contracts, native constraints and approval requirements. Unresolved choices block the provisioning that depends on them.

When not to rely on it

  • As a source of validated results. The scenarios are proposals.
  • As a platform guarantee or service-level agreement.
  • Without checking current platform limits. The README says to verify OS, SKU, regional availability and limits for each case.
  • To claim 99.999% from a small sample, or to infer untested combinations from unrelated successes.
